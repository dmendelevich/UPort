# UPort — правила игры для Claude

UPort — семейный Telegram-бот для советов по портфелю (несколько брокеров, несколько владельцев). Рабочие заметки по архитектуре, истории решений и открытым вопросам — в [`Claude/`](Claude/00_index.md) (начни с `00_index.md`, там карта всех файлов) и в [`Claude/BACKLOG.md`](Claude/BACKLOG.md) (открытые задачи по трекам + журнал сделанного). Этот файл — не замена им, а короткая выжимка того, что должно соблюдаться в КАЖДОЙ сессии.

## Как мы работаем над темой (согласовано 2026-07-20, см. `Claude/01_workflow_rules.md`)

1. Тему и направление задаёт пользователь — не предлагать новые темы самостоятельно.
2. Фиксированная последовательность по каждой теме: (1) пользователь инициирует, (2) вместе смотрим, что уже сделано — **код и документация, не полагаться на память**, она могла устареть, (3) подробно обсуждаем принципы/алгоритм **без кода**, (4) код — только после явного подтверждения, что всё согласовано.
3. Код не готов, пока не протестирован (процедура тестирования — ниже).
4. Коммит — прямо в `master` (без PR), после завершения темы; **`git push` делать той же командой сразу после коммита, без отдельного запроса подтверждения** (решено 2026-07-30 — раньше пуш требовал отдельного явного "да" каждый раз, отменено по просьбе пользователя).
5. Перед любым `DELETE` на живой БД — сначала `SELECT` и осмотреть (проверить вообще ВСЕ таблицы с FK на удаляемую строку), даже "просто на всякий случай".
6. Если упёрлись в проблему, чей корень (измерение/параметр) может понадобиться ещё не раз — сразу строить переиспользуемый механизм получения этого корня, не решать только конкретный случай (решено 2026-07-30, пример — волатильность бумаги, всплыла и в PriceMoveWatcher, и в протухании приказов/алертов).
7. **В Треке A (инвестиционная аналитика) — режим "физик", не "инженер" (решено 2026-07-30).** Пользователь не может сам поставить задачу в этой предметной области — не ждать формулировки, а самому доходить до нужного вопроса через анализ явления, объяснять ход рассуждения понятным языком и вместе с пользователем вырабатывать план решения. В остальных треках (B/C) пользователь ставит задачу сам — это нормально, не менять.

## Процедура работы над экранами/"кубиками" (отработана на нескольких темах, использовать всегда)

1. **Найти ВСЕ живые варианты** экрана/функционала по всей кодовой базе через `grep` — не по памяти. Один и тот же экран часто оказывается достижим из нескольких мест с независимыми реализациями.
2. Разобрать общее (кандидат в переиспользуемую функцию) vs специфичное для контекста.
3. **Обсуждать пограничные случаи с пользователем явно**, не решать самостоятельно.
4. Раскладывать содержание не по "экранам", а по **смысловым блокам** — один и тот же блок может повторяться на разных экранах.
5. Общая функция-сборщик — в `bot_handlers/bot_screens.py` (текст) или `bot_handlers/bot_keyboards.py` (клавиатуры), **одна функция на тип сущности/блока**, не одна на всё приложение.
6. Мигрировать каждое найденное место **по одному**, не всё разом.
7. Тестировать **послойно**, не только текстовым выводом в терминале:
   - прямой вызов новой функции на реальных данных БД (через `venv`);
   - мок-прогон полного хэндлера (`unittest.mock`, реальные `MenuAction`/DB);
   - реальное тестовое сообщение в Telegram (`aiogram.Bot`, `TELEGRAM_TOKEN` из `.env`) — для визуальных/ширинных решений терминал не показывает реальную картину (сам моноширинный).
8. После блока/темы — `restart_uport.sh` + проверка вживую самим пользователем. Реальные баги часто всплывают именно на этом шаге, не раньше.
9. Записывать решения в `Claude/BACKLOG.md` **сразу по ходу**, не откладывать до конца сессии.

## Принципы продукта (не пересматривать без явного решения пользователя)

- **UPort — advisory-only.** Советует, никогда сам не исполняет сделки/переводы. Дайджест — текстовые инструкции человеку, не нажатие кнопок за него.
- **Снэпшот, не архив — но только для того, что и так можно спросить у брокера/Yahoo.** Правило разделяет два разных вида истории: (1) рыночные данные и брокерские факты (котировки, сделки, ордера) — не хранить постоянно, запрашивать на лету, брокер/Yahoo уже это хранят; (2) история СОБСТВЕННЫХ решений и действий системы (планы входа/выхода, циклы стратегии) — нигде больше не существует, кроме как в UPort, и её осознанно стоит хранить. Исключения по виду (1) — `quote_snapshots` (короткий кольцевой буфер для `PriceMoveWatcher`). Пример вида (2), решено хранить — история циклов `order_pipelines` (см. `Claude/11_asset_lifecycle_and_plan.md`, согласовано 2026-07-29). Для нового похожего случая всегда решать явно, к какому виду он относится, не по умолчанию.
- Треки работы — A (Советник, главный), B (админ-интерфейс стратегий), C (наведение порядка) — см. `Claude/06_tracks.md`.

## Технические стандарты (не изобретать заново — см. `Claude/05_strategy_screen_and_kubiki.md` для полного описания)

- **Ширина экрана** — `SCREEN_WIDTH_CHARS = 22` (`bot_handlers/bot_screens.py`, откалибровано вживую на iPhone). `wrap_screen_line`/`wrap_param_line`/`justify_line` — готовые переносы/выравнивание. Шрифт Telegram пропорциональный — колонку чисел, которую нужно выровнять посимвольно, заворачивать в `` `code` ``-спан, не весь текст.
- **Кнопки** — отдельный LEGO-механизм в `bot_handlers/bot_keyboards.py` (`assemble_lego_line` + `build_*_block`), фиксированная ширина спецсимволами (`EN_SPACE`/`FIGURE_SPACE`/`BRAILLE_EMPTY`/`SIX_PER_EM`) — стабильна в любом шрифте, не только моноширинном.
- **Header/body/footer**: header — одна функция-сборщик на тип сущности (`format_strategy_header` и т.п.). Footer — порядок сверху вниз: (1) разделитель+фраза как единый опциональный блок (разделитель ТОЛЬКО если есть фраза), (2) переключатель вкладок (`generate_tab_switch_keyboard` — сам скрывает активную вкладку), (3) функциональные кнопки, (4) навигация (`generate_nav_back_keyboard`). У каждой вкладки — свой заголовок списка кнопок (часть footer, не body).
- **Время** — везде `TIMESTAMP(0) WITHOUT TIME ZONE`, хранение строго в UTC. SQL: `(CURRENT_TIMESTAMP AT TIME ZONE 'UTC')::timestamp(0)`. Python: `datetime.now(timezone.utc).replace(microsecond=0, tzinfo=None)`. Разницу дат считать в SQL (`EXTRACT`), не в Python — шлюз БД возвращает даты как JSON-строки.
- **Деньги/мультивалютность** — вся денежная информация выводится в `base_currency` СМОТРЯЩЕГО пользователя (`state: FSMContext` → `user_db_id` → `public.users.base_currency`), не в валюте листинга/брокера. Курс считается один раз за рендер и передаётся параметром во все блоки (или кэшируется по коду валюты, если в одном рендере несколько РАЗНЫХ исходных валют). `currencies.multiplier` — только для канонического слоя (`tickers`/Yahoo, нативные единицы биржи); `listings`/`assets`/`orders`/`alerts` (брокерский слой) уже в настоящих единицах, множитель не применять. `currency_rates` хранит курсы только к USD (хаб) — для другой пары нужна двухшаговая конвертация.
- **Конфигурация** — `config.py` для системных/технических параметров, `settings.py` для бизнес-порогов ("инвестиционный манифест"). Константы форматирования экрана (ширина и т.п.) — намеренно в `bot_screens.py`, не в `config.py` (не общесистемный параметр).
- **Имя бумаги под разные системы** — `tickers.ticker_name_map` (jsonb), ключ `brokers.short_name` (`FB`/`T212`) для брокеров и литерал `YAHOO` для Yahoo Finance, значение — как бумага называется именно там (пример: `{"FB": "AMGN.US", "T212": "AMGN", "YAHOO": "AMGN"}`) — см. `Claude/07_glossary.md`. Это актуальный механизм; `listings.broker_symbol` — пережиток той же информации по старой схеме, ещё используется местами в коде, подлежит выводу из употребления (см. `Claude/BACKLOG.md`, Трек C, п.23) — для нового кода ориентироваться на `ticker_name_map`, не заводить обращения к `listings.broker_symbol`.

## Проверять перед использованием

Память Claude между сессиями может устареть, а старые заметки в `ARCHITECTURE/` (`anal_core.md`, `tg_bot.md`, `ARCHITECTURE_tickers.md`) писались ДО совместной работы и местами прямо устарели (см. `Claude/BACKLOG.md`, Трек C). Перед тем как опираться на что-то из памяти или старых доков — свериться с реальным кодом.
