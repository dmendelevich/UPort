# Шлюз БД: находки и фикс + модуль создания портфеля (2026-07-21)

## Архитектура доступа к БД
Приложение НЕ подключается к Postgres напрямую — все модули (`database.py`: `db_bot`, `db_sys`) шлют HTTP `POST /query` в `uport_ai_gateway.py` (FastAPI + uvicorn, systemd `uport_gateway.service`), который **на каждый запрос открывает новое `psycopg2.connect()`**. Это ключевой факт, из которого следуют два разных вывода:

1. **RBAC по токену — реальный, нужный предохранитель.** Роли `AI`/`BOT`/`SYSTEM` определяются по `X-Token` в HTTP-заголовке и проверяются на СЕРВЕРНОЙ стороне шлюза (`query_lower.startswith(...)` на строки 55-72) — это не пережиток, а то, что делает `db_bot`/`db_sys` реальным разделением прав: сам Python-инстанс `db_bot` не "знает", что он read-only, разграничение работает только потому, что шлюз его enforces. Трогать не стали.

2. **`BEGIN`/`COMMIT`/`ROLLBACK` отдельными вызовами `execute_query()` — НЕ работает.** Раз каждый вызов — новое соединение, `db_sys.execute_query("BEGIN;")` и последующий `db_sys.execute_query("ROLLBACK;")` относятся к разным транзакциям в разных соединениях и никак не связаны. Всё, что происходит между ними, коммитится по факту сразу после каждого отдельного `execute_query()`. Единственный способ получить настоящую атомарность — **один `execute_query()` с несколькими SQL-операторами в одной строке** (так и сделано в `bot_utils.py:execute_virtual_transfer` — строка `BEGIN; UPDATE...; UPDATE...; COMMIT;`), либо ещё лучше — один запрос с data-modifying CTE (`WITH ... AS (INSERT ... RETURNING ...) ...`), который атомарен по своей природе без явного `BEGIN`/`COMMIT`.

**Обнаружено на практике:** `test_strategy_sync.py` полагался на многовызовный `BEGIN`/`ROLLBACK` для "стерильности" теста — на деле оставлял в БД реальные строки (`strategies.id=999`, тестовый `assets`, `strategy_assets`). Вручную вычищено 2026-07-21 после обнаружения. См. backlog #12 — сам `test_strategy_sync.py` и `test_bot_utils.py` ещё не переписаны на безопасный паттерн.

## Баг шлюза с потерей RETURNING-данных (починен)
`uport_ai_gateway.py` решал, вызывать ли `cur.fetchall()`, по эвристике `query_lower.startswith("select")`. Любой `WITH ...` (CTE) или голый `INSERT/UPDATE ... RETURNING` не начинается со слова `select` — гейтвей уходил в ветку "команда без результата", **коммитил изменения, но не читал `RETURNING`-строки**, отдавая вместо них generic `{"status": "success"}`. Данные при этом реально записывались — просто вызывающий код не мог их увидеть.

Исправлено на `cur.description is not None` (объективный факт от Postgres "есть ли колонки результата", не зависит от первого слова запроса) + безусловный `conn.commit()` после `fetchall()`. Не меняет поведение для уже работающих `SELECT`/`INSERT`/`UPDATE` без `RETURNING`. `uport_gateway.service` перезапущен, эффект подтверждён тестами.

## Модуль создания портфеля (`bot_handlers/portfolio_admin.py`)
- Доступен только `is_admin=true` (проверка на каждом хэндлере, как в `settings.py`).
- Вход: новая кнопка «➕ Создать портфель» в существующей панели `settings_main`.
- Кнопки везде отдают числовой ID сущности (`user_id`, `broker_id` — новые поля `MenuAction`), по общей договорённости.
- Экран подтверждения — переиспользует `generate_confirm_screen`/`generate_confirm_keyboard` (не изобретали новый).
- Создание — один атомарный CTE-запрос: `portfolios` + 2 строки `strategies` (`Кэш/Резерв` 10%, `Неопределенная стратегия` 90% — остаток, раз содержательных стратегий ещё нет) с копированием `rules_config`/`human_philosophy` из `strategy_templates` и простановкой `template_id`.
- **Важный паттерн для будущих multi-step FSM-экранов в этом проекте:** `is_admin`/`user_db_id` хранятся в FSM `state` и должны бережно сохраняться при любом `state.clear()` — иначе админ теряет доступ к панели до `/start`. Паттерн (уже был в `summary.py:process_back_to_menu`, применён и здесь): прочитать `is_admin`/`user_db_id` до `clear()`, затем `state.update_data(user_db_id=..., is_admin=...)` сразу после.
- Callback можно "отвечать" (`callback.answer()`) только один раз за колбэк — при делегировании в другой хэндлер (`process_cancel` → `process_settings_main`) не дублировать вызов.

## Конфликт роутеров: глобальный перехватчик текста (найдено пользователем вживую, починено)
`bot_handlers/ticker_search.py` содержит `@router.message(F.text)` — глобальный перехватчик "любой текст = тикер для справки", без ограничения по FSM-состоянию. Роутеры в `uport_ai_bot.py` пробуются в порядке регистрации; `ticker_search` был зарегистрирован раньше `portfolio_admin`, поэтому любой текст, отправленный на шаге ввода имени портфеля, доставался ticker_search, а не `process_name_text`. `backlog.py` с похожим FSM-вводом текста работал только потому, что его роутер регистрируется раньше ticker_search — везение порядка, не осознанная защита.

**Системный фикс** (не просто переставили порядок роутеров): `@router.message(StateFilter(None), F.text)` в `ticker_search.py` — перехватчик срабатывает только когда у пользователя НЕТ активного FSM-состояния. Теперь порядок регистрации роутеров больше не имеет значения для этого класса конфликтов — **любой будущий многошаговый экран с вводом текста** (создание стратегии, перераспределение долей и т.п. из бэклога #10/#11) автоматически защищён, без необходимости помнить про порядок `include_routers(...)`.

Протестировано напрямую через `HandlerObject.check()` (без сети): idle-чат → ticker_search матчится; состояние создания портфеля → ticker_search НЕ матчится, portfolio_admin матчится; состояние бэклога → ticker_search НЕ матчится, backlog матчится (регрессии нет).
