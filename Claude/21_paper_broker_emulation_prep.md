# Эмуляция брокера для бумажного портфеля — точка входа для НОВОЙ сессии (подготовлено 2026-08-15)

Сессия заканчивается по объёму темы, не по ресурсу — но тема сама выросла настолько, что заслуживает отдельного захода с чистого листа, не продолжения впроброс. Начни новую сессию с чтения ЭТОГО файла, а не с памяти — она могла устареть. Полный ход обсуждения (все находки, вся аргументация) — в этом же диалоге 2026-08-15, здесь — выжимка для старта.

## Как мы сюда пришли

Тема началась как мелкая правка интерфейса («дайджест как вкладка портфеля/стратегии») и по ходу доводки мелочей наткнулась на живой баг: кнопка «В список наблюдения» не пропадала у бумажного портфеля («ПБум») после добавления тикера. Починка бага потянула за собой вопрос пользователя — «а разве не должно быть либо карточка, либо инструкция по покупке?» — что вскрыло полный аудит различий между реальными портфелями (`execution_mode='ADVISORY'`) и бумажным (`execution_mode='CONFIRM'`). Аудит нашёл различий гораздо больше одной кнопки (см. «Инвентарь» ниже).

**Ключевой поворот принципа, вокруг которого теперь всё строится (сформулирован пользователем 2026-08-15):** не подгонять код приложения под обстоятельства бумажного портфеля («у него нет брокера — значит эта кнопка/вкладка/экран для него будет другой»), а держать код приложения **полностью идентичным** для обоих типов портфеля — и эмулировать снизу только БРОКЕРА, а не сам портфель. То есть «ПБум» должен работать так, как если бы у него был настоящий Freedom Broker — заявка эмулятора видится системой как обычное брокерское событие, а весь код экранов/аналитики/жизненного цикла плана вообще не должен знать про `execution_mode`.

Это не отменяет исходные принципы `14_paper_portfolio.md` (согласованы 2026-08-03) целиком — часть остаётся в силе, часть переосмысливается. См. раздел ниже.

## Что остаётся в силе из `14_paper_portfolio.md`, а что пересматривается

**Остаётся без изменений:**
- Advisory-only для РЕАЛЬНЫХ портфелей не нарушается — это вопрос только бумажного портфеля.
- `broker_id = NULL` у самого портфеля, синтетического брокера в таблице `brokers` заводить не нужно — листинги/цены бумажного портфеля и так используют реальный `broker_id=1` (ФБ) для получения котировок, это уже устоявшийся и рабочий приём (`ensure_listing(ticker_id, broker_id=1)`), эмуляция брокера НЕ про это, а про сам жизненный цикл ордера/плана.
- Владелец, стартовый капитал, срок, параметры портфеля — не затронуты этой темой.

**Пересматривается (открытый вопрос новой сессии, см. ниже):**
- Принцип №2 «Подтверждение, не мгновенное авто-исполнение» — раньше каждая рекомендация уходила отдельным Да/Нет сообщением. Если эмулируем БРОКЕРА, а не портфель, то по аналогии с реальным потоком подтверждение человека нужно только на решение «дать команду» (аналог похода в терминал брокера) — а не на каждый шаг лесенки (реальный брокер не спрашивает пользователя второй раз, когда лимитная заявка сама исполняется по достижении цены). Требует явного решения — см. вопрос 1 ниже.
- Весь код `bot_handlers/paper_execution.py` (`_execute_virtual_buy/_sell/_trim`, `send_paper_*_recommendations`, `paper_*_yes/_no`) — кандидат на замену эмулированным брокерским коннектором, а не самостоятельный параллельный движок.

## Как сегодня устроена граница с реальным брокером (проверено чтением кода 2026-08-15, не по памяти)

- **`FreedomBrokerClient`** (`brokers_connectors/fb_client.py`) — ТОЛЬКО читающие методы (`get_active_orders`, `get_quotes`, `get_active_alerts`, `get_security_info`, `find_ticker`). Метода «поставить заявку» нет и никогда не было — UPort принципиально не размещает ордера сам, человек ставит заявку в терминале брокера САМОСТОЯТЕЛЬНО, UPort только потом ЗАБИРАЕТ факт.
- **`database.py::sync_portfolio_orders(portfolio_id, account_number, api_orders)`** — пишет `public.orders` ИЗ ответа брокерского API (`api_orders`). Единственное место, где заводятся строки `orders`.
- **`brokers_connectors/sync_strategy_asset_fb.py::_update_pipeline_status`** — увидев (через WebSocket) изменение реальной позиции, продвигает `order_pipelines`: `current_step += 1` + `pipeline_status='ACTIVE'` (`NEXT_STEP`) или `pipeline_status='COMPLETED'` (`COMPLETE_PIPELINE`), снимает `pending_broker_order_id`.
- **`brokers_connectors/sync_account_fb.py`** — обновляет `accounts.cash_available` из брокерского баланса.
- **`analytics/ladder_step_watcher.py::LadderStepWatcher`** — уже ПОРТФЕЛЬ-АГНОСТИЧЕН (не смотрит на `execution_mode`!). Вызывается из общего 15-минутного цикла котировок (`sync_quotes_fb.py`), заново проверяет `trigger_conditions` текущего шага `strategy_tactics`, считает `suggested_qty`/`suggested_price` (по `listings.last_price`) — но СЕГОДНЯ при срабатывании условия только шлёт Telegram-уведомление и проставляет `step_ready_notified_at`, ничего не исполняет.
  - **Важная оговорка, найденная при чтении**: SQL этого вотчера делает `JOIN public.assets a ON a.portfolio_id = op.portfolio_id AND a.listing_id = op.listing_id` — то есть требует уже СУЩЕСТВУЮЩУЮ позицию. Значит сегодня он проверяет только ДОкупки к уже держащейся позиции, не самый первый вход (шаг 1). Это касается ОБОИХ типов портфеля одинаково, не специфика темы — но важно для дизайна эмулятора (см. вопрос 2).

## Инвентарь: где сегодня `execution_mode`/`CONFIRM` разветвляет код (полный список из аудита 2026-08-15, чтобы не искать заново)

**Группа A — операционный поток «рекомендация → покупка/продажа»:**
1. `bot_keyboards.py::generate_digest_section_keyboard` — кнопка `▶️ Исполнить` в дайджесте видна только при `execution_mode != 'CONFIRM'`.
2. `tickers.py` (вкладка «📋 План» карточки тикера, `sub_view=="plan"`) — у реальных полноценный трекер лесенки + диалоги «📝 План входа» (`plan_from_idea_start`) / «📋 План выхода» (`plan_exit_start`) / «🔗 Привязать ордер к плану» (`pipeline_link_start`); у `CONFIRM` вся вкладка ЦЕЛИКОМ подменяется на «Купить/Продать виртуально» с прямыми кнопками `paper_buy_yes`/`paper_sell_yes`.
3. Тот же путь — TRIM_DOWN: у реальных кнопки «Исполнить» для подрезки в дайджесте нет вообще (сознательно отложено, отдельная тема); у бумажных — `send_paper_trim_recommendations` с прямым Да/Нет.
4. Качество самой рекомендации: у реальных `digest_execute_buy/sell` (`order_pipelines.py`) считает цену/режим через `suggest_execution_terms` (Сигнал A — VWAP/момент исполнения); у бумажных `paper_buy_yes`/`paper_sell_yes` вообще не вызывает `suggest_execution_terms` — просто торгует по текущей `last_price`.
5. Ежедневный пуш устроен по-разному: реальные получают информационный дайджест (+опционально `▶️ Исполнить`); бумажные получают ОТДЕЛЬНЫЙ механизм — по сообщению на каждую рекомендацию (`send_paper_buy_recommendations`/`_sell_`/`_trim_`, `cron_scheduler.py::digest_clock_loop`).

**Группа B — атомарность исполнения (корень темы этого документа):**
6. `paper_execution.py::_execute_virtual_buy` пишет `order_pipelines` сразу как `pipeline_status='COMPLETED'`, шаг 1, вся сумма разом — у реального портфеля это `PENDING`→`ACTIVE`→...→`COMPLETED` по шагам `strategy_tactics`, растянуто во времени, управляется реальным исполнением брокера.

**Группа C — независимые мелкие расхождения, НЕ про операцию покупки, тривиальные фиксы, ещё НЕ сделаны:**
7. `bot_handlers/summary.py::process_test_summary_callback` («Тестовый капитал») сознательно не показывает кнопку «🏦 Счета» (комментарий «у бумажного портфеля один простой виртуальный счёт... экран «Счета» здесь не имеет смысла»). Пользователь: убрать разницу, использовать тот же код, что и у «Общей сводки капитала» (`process_family_summary_callback`). Нюанс, ранее обсуждённый и принятый: `process_view_accounts` устроен по ВЛАДЕЛЬЦУ, не по портфелю — кнопка «Счета» с «Тестового капитала» покажет РЕАЛЬНЫЕ брокерские счета того же владельца (у ДЛМ они есть) — это осознанно нормально, не баг.
8. `cron_scheduler.py::snapshot_portfolio_values` — фильтр `WHERE execution_mode = 'CONFIRM'` можно убрать (функция уже написана портфель-агностично, автор кода сам отметил это как готовую к расширению точку). Пользователь согласен убрать различие.

**Группа D — уже одинаково, аудитом подтверждено, трогать не нужно:**
`CashDeploymentAdvisor`/`PositionExitEvaluator`/`PortfolioRebalancer`/`LadderStepWatcher` не знают про `execution_mode` вообще — кормят одними и теми же рекомендациями оба потока. `capital_protection_watcher`/`price_move_watcher` фильтруют по брокеру ЛИСТИНГА (`lt.broker_id`), не портфеля — уже накрывают позиции бумажного портфеля наравне с реальными. `send_daily_digests` рассылается по ВСЕМ портфелям одним циклом.

## Целевая архитектура (набросок для обсуждения, НЕ детализировано, НЕ решено)

Идея: эмулированный брокерский коннектор (`brokers_connectors/paper_broker_*.py` или похожее имя), который на том же 15-минутном цикле котировок, что и `LadderStepWatcher`, при срабатывании условия шага:
1. Заводит синтетическую запись, эквивалентную «человек поставил заявку у брокера» (аналог того, что обычно попадает в `public.orders` через `sync_portfolio_orders`).
2. Сразу или с задержкой «исполняет» её — пишет в `assets`/`strategy_assets`/`accounts.cash_available` теми же принципами, что `SyncStrategyAssetFB`/`sync_account_fb.py` делают для реальных, и продвигает `order_pipelines` через тот же `_update_pipeline_status`-эквивалент (`NEXT_STEP`/`COMPLETE_PIPELINE`).
3. После этого код экранов (`tickers.py` вкладка «План», `order_pipelines.py`, дайджест) видит план бумажного портфеля СТРУКТУРНО так же, как план реального — лесенка, шаги, статусы — без единой ветки `if execution_mode == 'CONFIRM'`.

Это устраняет разом группы A (пп.1-5) и B — они перестают быть развилками кода приложения, потому что развилка уходит на один уровень ниже, в `brokers_connectors/`.

## Открытые вопросы — НЕ решать без пользователя, обсудить в САМОМ НАЧАЛЕ новой сессии

1. **Нужно ли по-прежнему Да/Нет-подтверждение, и на каком именно шаге?** Только на решение «завести план» (аналог похода в терминал, как «📝 План входа» у реального), после чего дальнейшие шаги лесенки исполняются эмулятором молча (как реальная лимитка сама исполняется по достижении цены, без повторного вопроса) — или подтверждение нужно на КАЖДЫЙ шаг?
2. **Шаг 1 (первый вход)** — `LadderStepWatcher` сегодня требует уже существующую `assets` (см. оговорку выше), то есть НЕ проверяет самый первый вход ни у реального, ни у бумажного портфеля. Расширять запрос вотчера, чтобы шаг 1 (обычно `mode: market`) тоже проверялся тем же кодом — или оставить отдельный немедленный путь именно для входа?
3. **Нужна ли синтетическая строка в `public.orders`** (со схемой `broker_order_id`, гарантированно не пересекающейся с реальными — например отрицательный диапазон или отдельная пометка) — для максимальной верности «как будто реальный брокер» — или эмулятор может писать сразу в `assets`/`order_pipelines`, минуя представление «ордера» как отдельной сущности (более простой, но менее честный вариант)?
4. **Проверка достаточности кэша** — у реального в этой точке проверять нечего (советует, не торгует); у эмулированного нужно проверить `accounts.cash_available` перед исполнением. Что делать при нехватке денег именно в момент срабатывания — пропустить цикл и попробовать позже, или отменить/пометить шаг как несостоявшийся?
5. **Кнопка «🔗 Привязать ордер к плану»** — у бумажного она либо не нужна вовсе (эмулятор сам знает, для какого плана заявка, линкует автоматически), либо остаётся видимой, но уже привязанной (эмулятор делает то же действие программно, что кнопка делает вручную) — на выбор.
6. **Уведомление об исполнении** — бумажному, видимо, всё равно нужно сообщение в Telegram («🪜 Шаг исполнен виртуально: N шт по $X»), просто без кнопок Да/Нет, раз действие уже совершено автоматически — согласовать формулировку и момент отправки.
7. **Объём первого захода** — реализовать сначала только ПОКУПКУ/вход (как исходная Фаза 2 `14_paper_portfolio.md` — только `CashDeploymentAdvisor`), или сразу закладывать эмулятор так, чтобы SELL/TRIM легли на ту же инфраструктуру без переделки (они устроены по группе A так же, просто зеркально)?

## Группа C — можно сделать отдельно и раньше, не дожидаясь решения по эмулятору

Оба фикса из «Группы C» выше НЕ зависят от архитектуры эмуляции брокера — их можно взять в любой момент, включая начало новой сессии одним небольшим первым шагом перед основной темой, если пользователь захочет размяться:
- Убрать фильтр `execution_mode = 'CONFIRM'` в `cron_scheduler.py::snapshot_portfolio_values`.
- Показать кнопку «🏦 Счета» и на экране «Тестовый капитал» (`summary.py::process_test_summary_callback`) — тем же кодом, что у «Общей сводки капитала».
