# Универсальные view (создано 2026-07-20)

## Проблема
По всему коду (15+ файлов: `bot_handlers/*`, `analytics/*`, `brokers_connectors/*`, `site_connectors/*`, `database.py`) вручную дублировался один и тот же JOIN `listings ↔ tickers` и его продолжения на `assets`/`watchlist`/`orders`/`strategy_assets`. Риск расхождений при правках, лишний объём кода.

## Решение
Слоистый набор PostgreSQL VIEW, каждый — **плоское соединение без бизнес-логики** (в отличие от уже существовавшего вычислительного `strategy_exposure`, который считает USD-доли с ETF look-through и остаётся отдельно).

- **Слой 0** — `v_listings_tickers`: один листинг бумаги у брокера + все поля `tickers` (через `t.*`, чтобы не требовать правки view при будущей чистке колонок tickers, см. backlog #4).
- **Слой 1** (каждый JOIN'ится к `v_listings_tickers`):
  - `v_assets_full` — одна реальная позиция (холдинг) в портфеле + владелец/портфель
  - `v_watchlist_full` — одна запись вотчлиста + `active_alerts_count` (простой скалярный подзапрос-агрегат — договорились, что лёгкие агрегаты допустимы)
  - `v_orders_full` — один ордер
  - `v_order_pipelines_full` — один шаг пайплайна исполнения по стратегии
- **Слой 2** — `v_strategy_assets_full`: доля одной позиции, закреплённая за стратегией (JOIN'ится к `v_assets_full`).

Скрипт создания: [`create_universal_views.py`](../create_universal_views.py) (по образцу `one_time_migrator.py` — идемпотентный, `DROP VIEW IF EXISTS ... CASCADE` перед созданием, запускается вручную через `db_sys`).

## Принципы, которые важно помнить
1. **Не делать один view на всё.** Таблицы связаны как «один ко многим» на разных уровнях (тикер → листинги → холдинги/вотчлист/ордера → доли в стратегиях). Один плоский JOIN всего сразу даёт математически неверные агрегаты из-за перемножения строк (fan-out). Поэтому view — по числу реальных «единиц» данных (бумага / позиция / запись вотчлиста / ордер / доля стратегии), а не один универсальный.
2. **Каждый view — full self-service.** Не нужно ничего доджойнивать руками: `v_assets_full` уже содержит все поля тикера и листинга.
3. **Критично избегать коллизий имён колонок.** Приложение читает результаты через `RealDictCursor` (`database.py` → gateway `uport_ai_gateway.py`) — то есть строки превращаются в **словари**. Одинаковые имена колонок в SELECT молча затирают друг друга (последняя побеждает, без ошибки). Поэтому:
   - у `tickers` (через `t.*`) поле `id` остаётся как есть и по конвенции читается как «id тикера»;
   - у всех остальных таблиц на каждом слое их собственный `id` **всегда** алиасится в `<table>_id` (`asset_id`, `watchlist_id`, `order_id`, `pipeline_id`, `strategy_asset_id`), чтобы не столкнуться с «тикерным» `id`, унаследованным через `lt.*`/`va.*`.
   - аналогично разведены все прочие пересекающиеся имена (`currency_id`, `last_updated_at`, `name`, `broker_id` и т.д.) — см. явные алиасы в `create_universal_views.py`.
4. **strategy_exposure не трогаем** — он остаётся единственным «вычислительным» view (конвертация валют, ETF look-through, агрегация в USD). Новые view — только для навигации/чтения сырых данных.

## Известные краевые случаи
- В `bot_handlers/watchlist.py` для служебного портфеля 9999 было отдельное правило подсчёта алертов (без фильтра `portfolio_id`, по всем портфелям на листинге). В `v_watchlist_full` этот хак сознательно не воспроизведён — используется единая логика (`al.portfolio_id = w.portfolio_id`) для всех портфелей. На реальных данных на 2026-07-20 это не расхождится (у портфеля 9999 пока нет записей в вотчлисте), но при переносе `watchlist.py` на новый view это надо учитывать. Портфель 9999 и так в backlog на удаление (#2).

## Результаты тестирования (2026-07-20)
- Все 6 view созданы без ошибок, `\d+` подтверждает отсутствие дублей колонок в каждом.
- Число строк каждого view 1:1 совпадает с исходной таблицей (listings=37, assets=19, watchlist=38, orders=3, order_pipelines=1, strategy_assets=20) — подтверждает отсутствие fan-out.
- `v_watchlist_full` для portfolio_id=1 даёт результат, побайтово идентичный старому ручному запросу из `watchlist.py`.
- Прогон через `db_bot.execute_query` (боевой слой приложения) подтвердил отсутствие коллизий ключей словаря на реальных данных.

## Не сделано (сознательно, отдельная задача)
Существующий код (`bot_handlers/*`, `analytics/*` и т.д.) **не переведён** на новые view — они пока только созданы в БД. Переключение старых ручных JOIN на view — это следующий отдельный шаг, requires обсуждения (какие файлы, в каком порядке, как тестировать после каждого).
