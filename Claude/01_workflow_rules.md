# Правила взаимодействия (согласовано 2026-07-20)

1. Тему и направление движения задаёт пользователь. Claude не инициирует новые темы самостоятельно.
2. По каждой теме — фиксированная последовательность:
   1. Пользователь инициирует тему.
   2. Совместно изучаем, что уже сделано (код, документация).
   3. Подробно обсуждаем и согласовываем принципы и алгоритмы — **без написания кода** на этом этапе.
   4. Только после явного подтверждения пользователем, что все детали согласованы, начинается работа с кодом.
3. Код не считается готовым, пока не протестирован.
4. GitHub (`https://github.com/dmendelevich/UPort`, remote `origin`) обновляется после завершения темы — прямыми коммитами в `master` (без Pull Request, как и вся текущая история репозитория). `git push` — той же командой сразу после коммита, без отдельного запроса подтверждения. *(согласовано 2026-07-21, отменено требование подтверждения — 2026-07-30)*
5. **Если в ходе темы упёрлись в проблему — искать её КОРЕНЬ, а не только решать конкретный случай, и сразу строить механизм получения/измерения этого корня как переиспользуемый фундамент.** Способность, скорее всего, понадобится ещё не раз. Пример, на котором сформулировано (2026-07-30): вопрос "как нормализовать порог по волатильности конкретной бумаги" всплыл независимо в PriceMoveWatcher и в протухании приказов/алертов — за один присест решили его один раз как общий примитив, а не дважды по отдельности. Это же объясняет, почему в проекте периодически находятся "заложенные, но не подключённые" механизмы (например, `strategy_assets.expected_quantity`) — принцип уже частично соблюдался неявно, теперь формализован явно.
6. **В инвестиционной аналитике (Трек A) — режим мышления "физик", не "инженер" (согласовано 2026-07-30).** Пользователь формулирует это как разницу подготовки: инженер решает уже поставленную техническую задачу, физик сначала анализирует явление, САМ формулирует из анализа задачу, объясняет ход рассуждения понятным языком и только потом вместе с заказчиком вырабатывает план решения. Пользователь — профан в инвестициях осознанно (не может сам поставить задачу в этой области, в отличие от остальных треков), поэтому именно в Треке A ожидается не ждать формулировки задачи, а самому доходить до неё через анализ проблемы и предъявлять пользователю. Уже отработано на практике до формализации правила: разбор "что значит 'резкое падение, требующее вмешательства'" для PriceMoveWatcher (2026-07-29/30) и разбор волатильности как общего примитива (2026-07-30, тот же день, что и правило 5 — оба принципа выросли из одного разговора: 5 про инфраструктуру, 6 про сам анализ). Не путать с остальными треками (B/C, инженерные по природе) — там пользователь ставит задачу сам и это нормально, менять не нужно.

Это правило продублировано в персональной памяти Claude (feedback), чтобы соблюдаться и в будущих сессиях.
