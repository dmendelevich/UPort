# Экран «Стратегии» и стандарт header/body/footer (2026-07-21)

## Идея пользователя
Портфель — техническая обвязка для совместимости с брокером, а реальный инструмент управления — стратегия внутри портфеля. Навигация: Портфель → список стратегий → карточка стратегии (по аналогии с уже существующими карточками портфеля/тикера).

## Архитектурный принцип: header/body/footer
Пользователь и раньше задумывал стандартизацию экранов ТГ на кубики: **header** (шапка сущности, одна на все экраны об этой сущности) — **body** (контент конкретного экрана/вкладки) — **footer** (навигация/кнопки). Инфраструктура для этого была начата (`bot_screens.py`, `bot_keyboards.py`, `bot_utils.py`), но реально применялась только частично — экраны `тикер и `портфель` продолжали строить header инлайн, с дублированием между вкладками.

Решение: не делать один header на всё (у тикера и стратегии физически разные данные), а **одну функцию-сборщик header на каждый тип сущности**, переиспользуемую всеми экранами об этой сущности. Экран стратегии — первый, полностью построенный по этому стандарту:
- `format_strategy_header(strategy_id)` (`bot_screens.py`) — шапка: имя стратегии, портфель/владелец, целевая доля, философия.
- `generate_tab_switch_keyboard(tabs, current_sub_view)` (`bot_keyboards.py`) — универсальный footer-переключатель вкладок (список пар `(текст, MenuAction)`, рендерит все, кроме текущей). Заменил ручной `if/elif/else` в `portfolios.py`, автоматически масштабируется на N вкладок.

Ретрофит существующих экранов (`portfolios.py`, `tickers.py`) под этот же стандарт — не сделан сейчас, в бэклоге (#13).

## Устройство новых экранов
- **Портфель → вкладка «🎯 Стратегии»** (`portfolios.py`, `sub_view="strategies"`): список активных стратегий портфеля с планом/фактом (план % / факт %), кнопка на каждую → карточка стратегии. Доступна только для реальных персональных портфелей (`p_id > 0 and p_id != 9999`) — у сводного (0) и виртуальной лаборатории (9999) нет собственных строк в `strategies`.
- **Карточка стратегии** (`bot_handlers/strategies.py`, новый файл, action `view_strategy`):
  - Header — `format_strategy_header`
  - План/факт капитала и риск-аудит лимитов — переиспользован существующий `analytics/portfolio_inspector.py::PortfolioInspector` (`get_virtual_cash_balances`, `audit_limits_and_rules`), ничего нового считать не пришлось
  - Список позиций — через `v_strategy_assets_full` (наш универсальный view, слой 2), каждая позиция — кнопка в существующую карточку тикера (`view_ticker`), стиль кнопки — существующий `generate_portfolio_button_text` (тот же LEGO-формат, что у списка активов портфеля)
  - Footer — существующий `generate_nav_back_keyboard`

## Правки по фидбеку с живого теста (2026-07-21, после первого restart_uport.sh)
Пользователь опробовал вживую, нашёл три момента:

1. **Сообщение о пустом списке бумаг было захардкожено под "Кэш/Резерв"**, а показывалось и для "Неопределенной стратегии". Починено: `strategies.py` теперь дополнительно тянет `system_key` шаблона (`JOIN strategy_templates`) и текст зависит от него (`CASH_RESERVE` → "это нормально для Кэш/Резерва", иначе — нейтральное "бумаг пока нет"). Не хардкодим по имени стратегии (оно текстовое и может быть переименовано пользователем) — только по стабильному `system_key`.

2. **Не было пути назад из тикера в стратегию.** Клик по бумаге из карточки стратегии уводил в карточку тикера, а там кнопка "назад" вела в общий список активов портфеля, теряя контекст. Финальная кнопка "назад" в `tickers.py` теперь проверяет `strategy_id > 0` первым приоритетом (до `is_owner_view`/`is_family_view`) и ведёт в `view_strategy`.

3. **Список стратегий не использовал LEGO-конвейер выравнивания** (`bot_keyboards.py`) — собирался обычной f-строкой, колонки плана/факта не выравнивались бы между разными по длине названиями стратегий. Добавлен новый микро-станок `build_name_block(name, width=24)` — по духу как `build_ticker_block`, но для произвольного текста переменной длины (тикеры ограничены 5 символами доменной моделью, названия стратегий — нет; длинные обрезаются многоточием). Добавлен высокоуровневый `generate_strategy_button_text(name, target_pct, actual_pct)`. Проверено: итоговая строка кнопки — ровно 44 символа независимо от длины названия и значений процентов (от "Кэш/Резерв" до "Стратегия следования за трендом").

Все три фикса протестированы мок-прогоном: сообщение для UNALLOCATED больше не упоминает Кэш/Резерв, у CASH_RESERVE сообщение сохранилось верным, `strategy_id` подтверждённо доходит до кнопки "Назад к стратегии" и переживает переключение вкладок тикера, LEGO-строки кнопок стратегий — фиксированной длины.

## Стандарт формата экранов расширен на текст тела/шапки (2026-07-25)

**Принцип, согласованный пользователем: всё построение экранов (шапка/тело/подвал) должно постепенно переезжать из кода отдельных `bot_handlers/*.py` в общие переиспользуемые функции `bot_screens.py`/`bot_keyboards.py` — не писать вёрстку экрана инлайн в обработчике.** Это распространение принципа header/body/footer (см. выше) на сам текст, не только на структуру экрана. Повод — полный разбор всех вариантов карточки тикера (см. BACKLOG.md #19, дополнено 2026-07-25): 4 живых независимых реализации шапки с разным стилем, найденные попутно два бага (пропавший footer в `ticker_search.py`, битый Markdown/HTML в `format_premium_header`).

Начали с `format_premium_header` (`bot_screens.py`) как эталонной реализации. Найденные и согласованные технические решения:

- **`SCREEN_WIDTH_CHARS = 35`** — константа живёт в начале `bot_screens.py` (НЕ в `config.py` — не общесистемный параметр, а локальный для принятия решения "влезает/не влезает строка"). Пользователь явно поправил решение поместить её в `config.py`.
- **`SEPARATOR_WIDTH_CHARS = 15`** — отдельная, более короткая константа специально для декоративной разделительной черты (`SEPARATOR_LINE`) — полная ширина 35 визуально "уезжала" при живом тесте в Telegram. Общая для всех шапок (используется и в `format_strategy_header`).
- **`wrap_screen_line(prefix, content, width)`** — перенос ОДНОРОДНОГО текста (не набора параметров): жадно заполняет первую строку по словам, продолжение — с висячим отступом длиной в `prefix`; если разрыв случайно пришёлся сразу после "—", дублирует разделитель в начале следующей строки.
- **`wrap_param_line(prefix, params, separator)`** — перенос строки из НЕСКОЛЬКИХ параметров, соединённых разделителем (например, "Сектор — Индустрия"): параметры не рвутся по словам между собой — первый остаётся на основной строке (с разделителем в конце), каждый следующий — на своей строке, прижатой ВПРАВО ровно до `width`-го знакоместа, с разделителем перед ним.
- **`justify_line(left, right, width)`** — прижимает левую часть строки влево, правую — вправо (например, тикер и цену), считая ширину по _видимой_ длине (`_visible_length` вычитает markdown-разметку `**`/`*`/`_` — иначе разметка исказила бы расчёт отступа).

**Важный технический нюанс, зафиксированный в обсуждении:** шрифт сообщений Telegram (в отличие от кнопок) пропорциональный, не моноширинный — посимвольное выравнивание (`justify_line`/`wrap_param_line`) даёт согласованное число знаков, но не идеально совпадающий пиксельный край. Моноширинный блок (тройные обратные кавычки Markdown) решил бы это полностью, но ценой потери жирного/курсива и правильного рендера эмодзи внутри блока — сознательно решили НЕ применять его здесь, посимвольного выравнивания достаточно. Проверено визуально мокапом сообщения Telegram (не только текстовым выводом в терминале, который сам по себе моноширинный и скрыл бы эту разницу).

Тестирование — на живых реальных тикерах (GLDM с реальным листингом у ФБ, TFX без листинга вообще → корректный переход на живую цену Yahoo Finance), без создания тестовых записей в БД (только чтение).

## Починен битый Markdown/HTML в `strategy_resolver.py` (2026-07-25)

Перед фиксом сохранена копия старой версии — [archive/strategy_resolver_pre_markdown_fix_2026-07-25.py](../archive/strategy_resolver_pre_markdown_fix_2026-07-25.py).

Пользователь вспомнил (не точно): раньше при отрицательном `quantity` при переносе между стратегиями "минус что-то ломал" в отправке сообщения, из-за чего этот экран когда-то перевели на `parse_mode="HTML"`. Проверка боем показала: **дело было не в знаке количества**, а в постороннем совпадении. Диагностика:
1. Собрал реальный `MenuAction` с отрицательным числом в `sub_view` (`"1/-30"`) — `pack()`/`unpack()` (исходники `aiogram.filters.callback_data`) режут строку по `:`, знак `-` никак не мешает. Не источник проблемы.
2. Отправил тестовое сообщение с `confirm_text` (там как раз есть `-30`) через `parse_mode="Markdown"` на живой Telegram API — ушло успешно (200, ok).
3. Отправил тестовое сообщение с `success_text` (тем же `parse_mode="Markdown"`) — **упало** с реальной ошибкой Telegram `can't parse entities: Can't find end of the entity`. Нашлась причина: в тексте ровно одно `_` — в служебном слове `db_sys` ("...через шлюз db_sys."). В обычном Markdown `_` — маркер курсива; непарное подчёркивание в написанном руками тексте (не в данных из БД) и есть настоящий источник давней путаницы — знак `quantity` тут ни при чём, совпадение по времени тестирования.

**Фикс:** `strategy_resolver.py` переведён на `parse_mode="Markdown"` (как везде), `<b>` → `**`, `db_sys` обёрнут в обратные кавычки (`` `db_sys` `` — code-span, внутри него `_` безопасен). Проверено повторной отправкой исправленного текста на живой Telegram API — 200, ok, Telegram подтвердил корректные сущности (`bold` + `code`). Реальный перенос между стратегиями (`execute_virtual_transfer`) не запускался — только текстовые сообщения, без изменения `strategy_assets`.

**Урок на будущее:** при написании текста для Telegram-сообщений вручную — technical-термины с подчёркиванием (`db_sys`, `execute_row` и т.п.) всегда оборачивать в обратные кавычки, а не писать как обычный текст, если используется `parse_mode="Markdown"`.

## Человеческий текст вместо технического жаргона (2026-07-25)

Пользователь справедливо указал: экран успеха ("Транзакция зафиксирована... через шлюз `db_sys`") — не просто некрасиво, а бесполезно для обычного пользователя, который не программист. Заодно нашли, что текст ещё и **фактически врал** — источник переноса был жёстко подписан "Разбор Нераспределенных", даже если реальным источником была другая стратегия (имя источника вообще не запрашивалось из БД).

Исправлено: `success_text` в `strategy_resolver.py` теперь — "✅ Перенос выполнен.\n\n{qty} шт. {symbol} переведено из «{source_name}» в «{target_name}».", с реальными именами обеих стратегий и символом тикера, без единого технического термина.

Заодно убрана строка `"Будет произведен атомарный сдвиг долей в СУБД."`, жёстко приклеенная в конец **любого** экрана через общий `generate_confirm_screen()` — она попадала не только на перенос между стратегиями, но и на создание портфеля, и на привязку ордера к плану (`order_pipelines.py`), где вообще не имела смысла. Теперь `generate_confirm_screen()` не добавляет никакой обязательной технической приписки — какой текст видит пользователь, целиком определяет вызывающий код.

**Принцип на будущее:** текст, который видит пользователь, не должен содержать внутренние имена модулей/функций/переменных (`db_sys`, "СУБД", "атомарный сдвиг" и т.п.) — только человеческое описание того, что произошло, в терминах его денег и стратегий.

## Модель footer — согласована широко, не только для карточки тикера (2026-07-26)

Пользователь предложил взглянуть на footer в принципе, для всех экранов UPort, не только тикера. Согласованная модель — footer состоит из следующих частей, сверху вниз, в этом фиксированном порядке:

1. **Разделитель + фраза (единый опциональный блок).** Разделитель показывается ТОЛЬКО если есть фраза -- если фразы нет, разделитель тоже не нужен (у него нет смысла в одиночку). Фраза -- один из трёх типов, не более одного одновременно:
   - инструкция/вопрос к кнопкам ниже (пример: "Включить инструмент в список наблюдения?", `ticker_search.py`);
   - результат уже проведённой операции (пример: "✅ Перенос выполнен.", `strategy_resolver.py`);
   - объяснение ошибки/ограничения, из-за которого экран урезан (пример: "⚠️ Не удалось пересчитать обоснование...", `strategies.py::process_view_idea_reason`).

   Явную инструкцию, дублирующую и без того понятное название кнопки, не пишем вообще -- чем меньше слов на маленьком экране телефона, тем лучше (принцип, уже действовавший при калибровке ширины header). К этой части применяются те же стандарты форматирования, что и к header (`SCREEN_WIDTH_CHARS`/`SEPARATOR_WIDTH_CHARS`, `wrap_screen_line` и т.п.).

2. **Информационные кнопки (переключатель вкладок).** Показывают расширенный вид ТОЙ ЖЕ сущности (например, «Владение и Ордера» / «Метрики Yahoo»). Одна строка, текущая вкладка скрывается -- для этого уже существует `generate_tab_switch_keyboard` (`bot_keyboards.py`), просто пока не везде используется (`tickers.py` показывает обе вкладки всегда, без скрытия текущей -- расхождение, ещё не исправлено).

3. **Функциональные кнопки.** Запускают действие над данными (например, «В список наблюдения», «Привязать ордер к плану», «Предложения»).

4. **Навигационные кнопки.** Одна кнопка -- назад на предыдущий экран, вторая -- в главное меню. Уже есть готовый `generate_nav_back_keyboard` (`bot_keyboards.py`).

Порядок рядов 1→2→3→4 зафиксирован как обязательный для всех экранов, не только карточки тикера. Найдено: сегодняшний код `tickers.py` уже неявно следует этому порядку для рядов 2→3→4 физически (сначала вкладки, потом функциональная кнопка "Привязать ордер", потом навигация) -- просто без переиспользуемого оформления, и с дублированием ручной сборки (в основном экране и отдельно в шторке алертов).

**Не решено (следующий шаг, не сейчас):** как оформить это в код -- единая функция-сборщик footer по образцу header, или несколько обязательных к вызову в этом порядке независимых кубиков (`generate_tab_switch_keyboard`/`generate_nav_back_keyboard` уже существуют для пп. 2 и 4; для п.1 и п.3 переиспользуемого стандарта пока нет).

## Footer-модель применена к `tickers.py` (2026-07-26)

Реализовано на основном экране (`process_view_ticker`) и шторке алертов:
- Ряд 2 (вкладки) переведён на `generate_tab_switch_keyboard` -- текущая вкладка теперь скрывается (раньше показывались обе всегда).
- Ряд 4 (навигация) переведён на один вызов `generate_nav_back_keyboard` вместо ручной сборки двух рядов по отдельности -- убрана дублирующая захардкоженная строка "📱 В главное меню".
- Шторка алертов: убран разделитель без фразы перед кнопками (по правилу "нет фразы -- нет разделителя"), footer тоже переведён на `generate_nav_back_keyboard` вместо ручной сборки той же формы с нуля.

Протестировано мок-прогоном всех 5 сценариев (owner/yahoo/family/research_portfolio/alerts) на реальных данных -- порядок и состав рядов кнопок соответствуют модели 2→3→4.

**Найдено попутно (не чинить точечно, см. BACKLOG.md #11):** для портфеля 9999 без конкретной стратегии footer показывает две одинаковые кнопки "главное меню" -- симптом того, что 9999 в принципе устаревшая концепция, ждущая полной вычистки.

## Почему `ticker_search.py`/`strategies.py` не нуждались в том же ретрофите (2026-07-26)

Пользователь спросил, почему footer-модель применили только к `tickers.py`. Проверка показала: `ticker_search.py` и `strategies.py` написаны ПОЗЖЕ, уже после появления `generate_nav_back_keyboard`/`generate_tab_switch_keyboard` (работа над экраном "Стратегии", 2026-07-21) -- у них с самого начала навигация шла через готовый кубик, дублирования как в `tickers.py` (который старше и как раз висел в BACKLOG #19 на ретрофит) там никогда не было. Табов (ряд 2) в этих экранах нет вообще -- нечего скрывать.

Единственное найденное реальное нарушение: `strategies.py::process_view_strategy` ставил разделитель перед списком кнопок бумаг без всякой фразы после него -- нарушение правила "нет фразы, нет разделителя". Убран.
