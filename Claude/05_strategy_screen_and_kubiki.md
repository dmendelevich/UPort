# Экран «Стратегии» и стандарт header/body/footer (2026-07-21)

## 📋 Шпаргалка перед следующей сессией: стандартизация body (подготовлено 2026-07-26)

Header и footer доведены до стандарта и протестированы вживую (см. хронологию ниже). Следующая тема — **body** (тело экрана, специфичный контент вкладки/контекста), решили начать с чистого листа в новой сессии. Это — конспект, чтобы не пересказывать вводные заново.

### Процедура, которой мы следовали для header/footer (использовать ту же для body)
1. **Найти ВСЕ живые варианты** экрана данного типа по всей кодовой базе через `grep` по характерным паттернам (повторяющиеся эмодзи-шапки, один и тот же `action` в разных файлах и т.п.) — не полагаться на память, перепроверять код каждый раз.
2. **Разобрать, что общее** между вариантами (кандидат в общую переиспользуемую функцию) и **что специфично** для контекста (остаётся в конкретном экране).
3. **Обсуждать пограничные случаи с пользователем явно**, не решать самостоятельно (например: что входит в общий header, а что — контекстная строка body).
4. Писать общую функцию-сборщик в `bot_screens.py` (текст) или `bot_keyboards.py` (клавиатуры) — по одной функции на тип сущности, не одна на всё.
5. **Мигрировать каждое найденное место** на общую функцию по одному, не пропускать молча.
6. **Тестировать прогоном реального хэндлера** (мок `callback`/`message`/`state` через `unittest.mock`) **на реальных данных из БД** — не изолированным вызовом функции. Оба реальных бага в этой теме (пропавший footer, битый Markdown) нашлись именно так.
7. **Для визуальных/ширинных решений — не доверять текстовому выводу в терминале** (он моноширинный и скрывает реальную картину). Отправлять настоящие тестовые сообщения в Telegram и калибровать по фактическому виду на экране пользователя (телефон — не то же самое, что терминал).
8. Записывать решения в заметки СРАЗУ по ходу, не откладывать.
9. Коммитить с сообщением, ссылающимся на заметки; в конце темы — предлагать restart живого сервиса и проверку вживую.

### Готовые строительные блоки (уже есть, переиспользовать)
`bot_handlers/bot_screens.py`:
- `SCREEN_WIDTH_CHARS = 22` — ширина строки для решения "влезает / нужно переносить" (откалибровано по реальному экрану iPhone 12, не наугад).
- `SEPARATOR_WIDTH_CHARS = 12`, `SEPARATOR_LINE` — декоративный разделитель, **сознательно короче** содержательной ширины (полноширинная черта "уезжала" визуально).
- `wrap_screen_line(prefix, content, width=SCREEN_WIDTH_CHARS)` — перенос ОДНОРОДНОГО текста (жадное заполнение по словам + висячий отступ под `prefix`).
- `wrap_param_line(prefix, params, separator=" — ", width=SCREEN_WIDTH_CHARS)` — перенос строки из НЕСКОЛЬКИХ параметров (не рвутся по словам между собой), второй параметр прижимается вправо ровно до `width`-го знакоместа.
- `justify_line(left, right, width=SCREEN_WIDTH_CHARS)` — прижимает левую часть влево, правую вправо; считает по ВИДИМОЙ длине (`_visible_length` вычитает `**`/`*`/`_`, иначе разметка портит расчёт отступа).
- `format_premium_header(ticker_id, portfolio_id=0)` — эталонный header тикера, единственный на все карточки.
- `format_strategy_header(strategy_id)` — эталонный header стратегии.

`bot_handlers/bot_keyboards.py`:
- `generate_tab_switch_keyboard(tabs, current_sub_view)` — footer ряд 2 (вкладки), текущая скрывается автоматически.
- `generate_nav_back_keyboard(one_step_back_text, full_back_callback)` — footer ряд 4, всегда 2 строки (динамическая "назад" + жёсткая "главное меню").
- LEGO-станки для кнопок (`build_name_block`/`build_finance_block`/`build_percent_block`/`build_number_block`/`build_separator_block`) — фиксированная ширина через спецсимволы-пробели (`EN_SPACE`/`FIGURE_SPACE`/`BRAILLE_EMPTY`), у которых стабильная ширина в ЛЮБОМ шрифте (не только моноширинном) — этим и пользуемся.

### Согласованная модель экрана
- **Header** — одна функция-сборщик НА ТИП СУЩНОСТИ (не одна на всё приложение), переиспользуемая всеми экранами про эту сущность.
- **Body** — контент конкретной вкладки/контекста, специфичный для каждого экрана. **Ещё не обсуждали стандарт** — тема следующей сессии.
- **Footer** — 4 части, строго в этом порядке сверху вниз (не все обязательны для каждого экрана):
  1. Разделитель + фраза — вместе, опционально; нет фразы → нет разделителя. Фраза — один из 3 типов: инструкция/вопрос к кнопкам ниже, результат уже проведённой операции, объяснение ошибки/ограничения. Не дублировать очевидное название кнопки словами.
  2. Информационные кнопки (переключатель вкладок той же сущности) — `generate_tab_switch_keyboard`.
  3. Функциональные кнопки (действие над данными).
  4. Навигация (назад + главное меню) — `generate_nav_back_keyboard`.

## Архитектурный принцип: header/body/footer
Пользователь и раньше задумывал стандартизацию экранов ТГ на кубики: **header** (шапка сущности, одна на все экраны об этой сущности) — **body** (контент конкретного экрана/вкладки) — **footer** (навигация/кнопки). Инфраструктура для этого была начата (`bot_screens.py`, `bot_keyboards.py`, `bot_utils.py`), но реально применялась только частично — экраны `тикер и `портфель` продолжали строить header инлайн, с дублированием между вкладками.

Решение: не делать один header на всё (у тикера и стратегии физически разные данные), а **одну функцию-сборщик header на каждый тип сущности**, переиспользуемую всеми экранами об этой сущности. Экран стратегии — первый, полностью построенный по этому стандарту:
- `format_strategy_header(strategy_id)` (`bot_screens.py`) — шапка: имя стратегии, портфель/владелец, целевая доля, философия.
- `generate_tab_switch_keyboard(tabs, current_sub_view)` (`bot_keyboards.py`) — универсальный footer-переключатель вкладок (список пар `(текст, MenuAction)`, рендерит все, кроме текущей). Заменил ручной `if/elif/else` в `portfolios.py`, автоматически масштабируется на N вкладок.

Ретрофит существующих экранов (`portfolios.py`, `tickers.py`) под этот же стандарт — не сделан сейчас, в бэклоге (#13).

## Правки по фидбеку с живого теста (2026-07-21, после первого restart_uport.sh)
Пользователь опробовал вживую, нашёл три момента:

1. **Сообщение о пустом списке бумаг было захардкожено под "Кэш/Резерв"**, а показывалось и для "Неопределенной стратегии". Починено: `strategies.py` теперь дополнительно тянет `system_key` шаблона (`JOIN strategy_templates`) и текст зависит от него (`CASH_RESERVE` → "это нормально для Кэш/Резерва", иначе — нейтральное "бумаг пока нет"). Не хардкодим по имени стратегии (оно текстовое и может быть переименовано пользователем) — только по стабильному `system_key`.

2. **Не было пути назад из тикера в стратегию.** Клик по бумаге из карточки стратегии уводил в карточку тикера, а там кнопка "назад" вела в общий список активов портфеля, теряя контекст. Решение: `strategy_id` теперь пробрасывается в `MenuAction` при переходе в `view_ticker` из карточки стратегии, и **дальше сквозь всю карточку тикера** — включая переключение её собственных вкладок ("Владение и Ордера" / "Метрики Yahoo"), чтобы контекст не терялся при листании тикера. Финальная кнопка "назад" в `tickers.py` теперь проверяет `strategy_id > 0` первым приоритетом (до `is_owner_view`/`is_family_view`) и ведёт в `view_strategy`.

3. **Список стратегий не использовал LEGO-конвейер выравнивания** (`bot_keyboards.py`) — собирался обычной f-строкой, колонки плана/факта не выравнивались бы между разными по длине названиями стратегий. Добавлен новый микро-станок `build_name_block(name, width=24)` — по духу как `build_ticker_block`, но для произвольного текста переменной длины (тикеры ограничены 5 символами доменной моделью, названия стратегий — нет; длинные обрезаются многоточием). Добавлен высокоуровневый `generate_strategy_button_text(name, target_pct, actual_pct)`. Проверено: итоговая строка кнопки — ровно 44 символа независимо от длины названия и значений процентов (от "Кэш/Резерв" до "Стратегия следования за трендом").

Все три фикса протестированы мок-прогоном: сообщение для UNALLOCATED больше не упоминает Кэш/Резерв, у CASH_RESERVE сообщение сохранилось верным, `strategy_id` подтверждённо доходит до кнопки "Назад к стратегии" и переживает переключение вкладок тикера, LEGO-строки кнопок стратегий — фиксированной длины.

## Стандарт формата экранов расширен на текст тела/шапки (2026-07-25)

**Принцип, согласованный пользователем: всё построение экранов (шапка/тело/подвал) должно постепенно переезжать из кода отдельных `bot_handlers/*.py` в общие переиспользуемые функции `bot_screens.py`/`bot_keyboards.py` — не писать вёрстку экрана инлайн в обработчике.** Это распространение принципа header/body/footer (см. выше) на сам текст, не только на структуру экрана. Повод — полный разбор всех вариантов карточки тикера (см. BACKLOG.md #19, дополнено 2026-07-25): 4 живых независимых реализации шапки с разным стилем, найденные попутно два бага (пропавший footer в `ticker_search.py`, битый Markdown/HTML в `format_premium_header`).

Начали с `format_premium_header` (`bot_screens.py`) как эталонной реализации. Найденные и согласованные технические решения:

- **`SCREEN_WIDTH_CHARS = 35`** — константа живёт в начале `bot_screens.py` (НЕ в `config.py` — не общесистемный параметр, а локальный для принятия решения "влезает/не влезает строка"). Пользователь явно поправил решение поместить её в `config.py`.
- **`SEPARATOR_WIDTH_CHARS = 15`** — отдельная, более короткая константа специально для декоративной разделительной черты (`SEPARATOR_LINE`) — полная ширина 35 визуально "уезжала" при живом тесте в Telegram. Общая для всех шапок (используется и в `format_strategy_header`).
- **`wrap_screen_line(prefix, content, width)`** — перенос ОДНОРОДНОГО текста (не набора параметров): жадно заполняет первую строку по словам, продолжение — с висячим отступом длиной в `prefix`; если разрыв случайно пришёлся сразу после "—", дублирует разделитель в начале следующей строки.
- **`wrap_param_line(prefix, params, separator)`** — перенос строки из НЕСКОЛЬКИХ параметров, соединённых разделителем (например, "Сектор — Индустрия"): параметры не рвутся по словам между собой — первый остаётся на основной строке (с разделителем в конце), каждый следующий — на своей строке, прижатой ВПРАВО ровно до `width`-го знакоместа, с разделителем перед ним.
- **`justify_line(left, right, width)`** — прижимает левую часть строки влево, правую — вправо (например, тикер и цену), считая ширину по _видимой_ длине (`_visible_length` вычитает markdown-разметку `**`/`*`/`_` — иначе разметка исказила бы расчёт отступа).

**Важный технический нюанс, зафиксированный в обсуждении:** шрифт сообщений Telegram (в отличие от кнопок) пропорциональный, не моноширинный — посимвольное выравнивание (`justify_line`/`wrap_param_line`) даёт согласованное число знаков, но не идеально совпадающий пиксельный край. Моноширинный блок (тройные обратные кавычки Markdown) решил бы это полностью, но ценой потери жирного/курсива и правильного рендера эмодзи внутри блока — сознательно решили НЕ применять его здесь, посимвольного выравнивания достаточно. Проверено визуально мокапом сообщения Telegram (не только текстовым выводом в терминале, который сам по себе моноширинный и скрыл бы эту разницу).

Тестирование — на живых реальных тикерах (GLDM с реальным листингом у ФБ, TFX без листинга вообще → корректный переход на живую цену Yahoo Finance), без создания тестовых записей в БД (только чтение).

## Починен битый Markdown/HTML в `strategy_resolver.py` (2026-07-25)

Перед фиксом сохранена копия старой версии — [archive/strategy_resolver_pre_markdown_fix_2026-07-25.py](../archive/strategy_resolver_pre_markdown_fix_2026-07-25.py).

Пользователь вспомнил (не точно): раньше при отрицательном `quantity` при переносе между стратегиями "минус что-то ломал" в отправке сообщения, из-за чего этот экран когда-то перевели на `parse_mode="HTML"`. Проверка боем показала: **дело было не в знаке количества**, а в постороннем совпадении. Диагностика:
1. Собрал реальный `MenuAction` с отрицательным числом в `sub_view` (`"1/-30"`) — `pack()`/`unpack()` (исходники `aiogram.filters.callback_data`) режут строку по `:`, знак `-` никак не мешает. Не источник проблемы.
2. Отправил тестовое сообщение с `confirm_text` (там как раз есть `-30`) через `parse_mode="Markdown"` на живой Telegram API — ушло успешно (200, ok).
3. Отправил тестовое сообщение с `success_text` (тем же `parse_mode="Markdown"`) — **упало** с реальной ошибкой Telegram `can't parse entities: Can't find end of the entity`. Нашлась причина: в тексте ровно одно `_` — в служебном слове `db_sys` ("...через шлюз db_sys."). В обычном Markdown `_` — маркер курсива; непарное подчёркивание в написанном руками тексте (не в данных из БД) и есть настоящий источник давней путаницы — знак `quantity` тут ни при чём, совпадение по времени тестирования.

**Фикс:** `strategy_resolver.py` переведён на `parse_mode="Markdown"` (как везде), `<b>` → `**`, `db_sys` обёрнут в обратные кавычки (`` `db_sys` `` — code-span, внутри него `_` безопасен). Проверено повторной отправкой исправленного текста на живой Telegram API — 200, ok, Telegram подтвердил корректные сущности (`bold` + `code`). Реальный перенос между стратегиями (`execute_virtual_transfer`) не запускался — только текстовые сообщения, без изменения `strategy_assets`.

**Урок на будущее:** при написании текста для Telegram-сообщений вручную — technical-термины с подчёркиванием (`db_sys`, `execute_row` и т.п.) всегда оборачивать в обратные кавычки, а не писать как обычный текст, если используется `parse_mode="Markdown"`.

## Человеческий текст вместо технического жаргона (2026-07-25)

## Модель footer — согласована широко, не только для карточки тикера (2026-07-26)

Пользователь предложил взглянуть на footer в принципе, для всех экранов UPort, не только тикера. Согласованная модель — footer состоит из следующих частей, сверху вниз, в этом фиксированном порядке:

1. **Разделитель + фраза (единый опциональный блок).** Разделитель показывается ТОЛЬКО если есть фраза -- если фразы нет, разделитель тоже не нужен (у него нет смысла в одиночку). Фраза -- один из трёх типов, не более одного одновременно:
   - инструкция/вопрос к кнопкам ниже (пример: "Включить инструмент в список наблюдения?", `ticker_search.py`);
   - результат уже проведённой операции (пример: "✅ Перенос выполнен.", `strategy_resolver.py`);
   - объяснение ошибки/ограничения, из-за которого экран урезан (пример: "⚠️ Не удалось пересчитать обоснование...", `strategies.py::process_view_idea_reason`).

   Явную инструкцию, дублирующую и без того понятное название кнопки, не пишем вообще -- чем меньше слов на маленьком экране телефона, тем лучше (принцип, уже действовавший при калибровке ширины header). К этой части применяются те же стандарты форматирования, что и к header (`SCREEN_WIDTH_CHARS`/`SEPARATOR_WIDTH_CHARS`, `wrap_screen_line` и т.п.).

2. **Информационные кнопки (переключатель вкладок).** Показывают расширенный вид ТОЙ ЖЕ сущности (например, «Владение и Ордера» / «Метрики Yahoo»). Одна строка, текущая вкладка скрывается -- для этого уже существует `generate_tab_switch_keyboard` (`bot_keyboards.py`), просто пока не везде используется (`tickers.py` показывает обе вкладки всегда, без скрытия текущей -- расхождение, ещё не исправлено).

3. **Функциональные кнопки.** Запускают действие над данными (например, «В список наблюдения», «Привязать ордер к плану», «Предложения»).

4. **Навигационные кнопки.** Одна кнопка -- назад на предыдущий экран, вторая -- в главное меню. Уже есть готовый `generate_nav_back_keyboard` (`bot_keyboards.py`).

Порядок рядов 1→2→3→4 зафиксирован как обязательный для всех экранов, не только карточки тикера. Найдено: сегодняшний код `tickers.py` уже неявно следует этому порядку для рядов 2→3→4 физически (сначала вкладки, потом функциональная кнопка "Привязать ордер", потом навигация) -- просто без переиспользуемого оформления, и с дублированием ручной сборки (в основном экране и отдельно в шторке алертов).

**Не решено (следующий шаг, не сейчас):** как оформить это в код -- единая функция-сборщик footer по образцу header, или несколько обязательных к вызову в этом порядке независимых кубиков (`generate_tab_switch_keyboard`/`generate_nav_back_keyboard` уже существуют для пп. 2 и 4; для п.1 и п.3 переиспользуемого стандарта пока нет).

## Стандартизация body карточки тикера (2026-07-26)

Header и footer закрыты (см. выше) -- следующий шаг по плану пользователя: содержательное тело (body) карточки тикера. Работа над этой темой заняла всю сессию 2026-07-26.

### Шаг 1-2: полный разбор всех экранов с тикером

По просьбе пользователя расширил поиск (не ограничиваясь одной карточкой): нашёл 4 самостоятельных "карточки" (header+body+footer) и 4 "строки-в-списке" (кнопка, представляющая тикер внутри списка из многих):
- **Карточки**: `tickers.py::process_view_ticker` (основная), `ticker_search.py::process_global_ticker_search` (быстрый поиск), `strategies.py::process_view_idea_reason` (обоснование идеи), `strategy_resolver.py::process_universal_confirm_screen` (подтверждение переноса -- вне темы, транзакционный диалог, не просмотр актива).
- **Строки-в-списке** (кнопка, не отдельный экран) -- отложены в `BACKLOG.md` №29 (три независимых LEGO-формата + расхождение в целевом экране "Предложений").

### Переосмысление: не "экран", а "смысловой блок"

Пользователь верно поправил первоначальный подход -- вместо категоризации по экранам разложили body на смысловые блоки, которые могут повторяться на разных экранах:
1. **Финансовая характеристика** -- цена входа vs текущая, объёмы (вложено/сейчас), прибыль, срок владения, годовая доходность.
2. **Поведение** -- % изменения цены за периоды + индикатор обвала.
3. **Компакт + "подробнее"** -- принцип отображения (не отдельный блок).
4. **Рыночные сигналы** -- тренд/RSI/SMA.
5. **Связь с брокером** -- алерты + ордера.
6. **Где ещё есть/запланировано** -- по портфелям или по стратегиям.
7. **Критерии стратегии** -- по итогу оказалось, что это принадлежит карточке СТРАТЕГИИ, не тикера (вне темы, будущая сессия).
8. **Совместимость со стратегиями** -- решено оставить только в `ticker_search.py`, не дублировать в основной карточке.
9. **Риск-аудит / обоснование идеи** -- контекстно-зависимый (уже существовал, встроен в новую архитектуру без изменений по сути).

Также решено: **строка контекста владения** ("В ПОРТФЕЛЕ X" / "В ОБЩЕМ КАПИТАЛЕ СЕМЬИ" и т.п.) убрана как отдельная сущность -- каждый блок несёт свою подпись сам (см. Блок 1/6 ниже). Экран подтверждения переноса (`strategy_resolver.py`) подтверждён как вне темы.

### Блок 1 -- `format_position_financials` (`bot_screens.py`)

Финансовая характеристика позиции. Параметр `strategy_id` переключает источник объёма: `NULL/0` -- вся позиция портфеля (`v_assets_full.quantity`), `>0` -- доля, закреплённая за стратегией (`v_strategy_assets_full.allocated_quantity`). Цена входа (`avg_price`) в обоих случаях общая портфельная -- у `strategy_assets` нет собственной цены входа (осознанное упрощение модели данных, подтверждено пользователем).

Формат (согласован живыми итерациями в Telegram): подпись владения (портфель ИЛИ стратегия, коротко) + объём — одной строкой прижато по краям (как тикер/цена в шапке); "Вход:"/"Сейчас:" каждое на своей строке с переносом сразу после двоеточия (не words-wrap); прибыль; срок владения + годовая доходность. Названия стратегий сокращены до предельно коротких (`STRATEGY_MICRO_LABELS`: "Револьвер.", "Консерв.", "Тренд.", "Неопред.", "Кэш/Резерв") -- отдельный, более агрессивный набор, чем `SHORT_STRATEGY_LABELS` в `portfolios.py` (там место под кнопку шире).

### Блок 6 -- `format_cross_holdings` (`bot_screens.py`)

"Где ещё в семье есть/запланировано" -- за вычетом текущего контекста (уже показан Блоком 1). Тот же переключатель `strategy_id`, что у Блока 1, но переключает не объём одной позиции, а РАЗРЕЗ списка:
- `strategy_id>0` -- по СТРАТЕГИЯМ: холдинги через `v_strategy_assets_full`, план -- через `order_pipelines` (ладдер стратегии может существовать ещё без реального ордера у брокера).
- `strategy_id==0` -- по ПОРТФЕЛЯМ: холдинги через `v_assets_full`, план -- через РЕАЛЬНЫЕ активные ордера у брокера (`public.orders`), не `order_pipelines` -- на уровне портфеля важен факт "выставлена ли заявка", а не абстрактный план стратегии (уточнено пользователем).

Направление плана (покупка/продажа/Stop Loss/Take Profit) показывается через ту же категоризацию, что и в Блоке 5 (`classify_order`/`ORDER_CATEGORIES`), знаком количества (продажа/SL/TP -- минус). Формат строки: `"{направление} у {владелец} ({контекст}): {qty} шт."`.

Заменил собой прежний ad hoc код `is_family_view` ("Распределение по счетам семьи" с полным P&L на holder) и глобального research ("Семейный кросс-радар") -- в Блоке 6 без долларовых сумм, только объём (P&L уже в Блоке 1 для своей позиции).

### PriceMoveWatcher -- реализация индикатора резкого движения цены (2026-07-26)

Стаб "🚧 Индикатор обвала: в разработке" (Блок 2) заменён на настоящий механизм. Обсуждение с пользователем прошло несколько раундов пересмотра дизайна ("критикуй") -- итоговые решения:

- **Хранение** -- отдельная таблица `public.quote_snapshots` (`listing_id, price, recorded_at`), НЕ JSONB-поле в `listings` (пользователь верно указал: JSON заставляет вручную парсить/обрезать список в Python, а таблица даёт то же через SQL и устойчивее к пропущенным циклам синка). Кольцевой буфер -- вручную (Postgres не имеет для этого встроенного механизма): после каждой вставки удаляются самые старые строки сверх `PRICE_MOVE_WATCHER_BUFFER_SIZE`.
- **Окно времени, не число отсчётов** -- `PRICE_MOVE_WATCHER_WINDOW_MINUTES` (45) в `settings.py`, расчёт ищет ближайшую по времени котировку не позже "N минут назад" по `recorded_at`, а не N-ю по счёту запись. Это специально отвязано от размера буфера (20, "с запасом") -- если частота синка котировок (`QUOTES_SYNC_INTERVAL`, `cron_scheduler.py`) изменится, окно в минутах останется верным само по себе.
- **Переиспользуемая логика** -- `analytics/quote_snapshot_utils.py` (`record_quote_snapshot`, `compute_price_move`), отдельно от алертов/уведомлений, чтобы этот же расчёт "% движения за окно" можно было использовать и в критериях стратегий позже (идея пользователя, не реализовано сейчас).
- **Поля алертов -- взяты из реального словаря полей ФБ**, который предоставил пользователь (`trigger_type`: `moving_down_from_current`/`moving_up_from_current` -- те же значения, что использует сам брокер для похожих условий, не изобретали новые; `expire_type='0'` -- "до отмены", тоже реальное значение ФБ; `condition_type` -- поле, которое пользователь сам добавил поверх схемы ФБ как упрощение, использовано как `"-"`/`"+"`, что естественно ложится на уже существующую ветку отображения `trigger_pct` в Блоке 5 без правок кода отображения; `periodic` -- переиспользовано поле ФБ (секунды до повтора уведомления) вместо отдельного самодельного cooldown; `is_active`/`source_type` -- поля, которые пользователь добавил сам поверх схемы ФБ, использованы: `source_type='uport'` (по прецеденту из устаревшего `analytics/old_stuff/ai_strategist.py`), `is_active=True` = "взведён" (может повторяться по `periodic`, пока не остановлен), `is_active=False` = "снят" (пользователь нажал "Остановить" ИЛИ движение цены разрешилось само).
- **Кнопка "Остановить"** -- новое поле `MenuAction.alert_id` (`bot_handlers/common.py`), новый хэндлер `tickers.py::process_stop_price_alert` (action=`stop_price_alert`) -- ставит `is_active=false`, вотчер это видит и прекращает повторы.
- **Область действия** -- запись алерта остаётся на уровне портфель+листинг (как у брокерских алертов, НЕ добавляли `strategy_id` в схему `alerts` -- избегаем задваивания уведомлений, если бумага разбита между несколькими стратегиями одного портфеля), но **текст уведомления стратегийно-осведомлён** -- подтягивает из `strategy_assets`, в какой стратегии(-ях) этого портфеля лежит бумага (реальная единица управления, см. `Claude/05_...` выше).
- **Вызывается** из `sync_quotes_fb.py`, после обновления котировок -- по тому же принципу, что `stale_order_watcher.py`/`ladder_step_watcher.py` (рыночно-зависимая проверка, не дайджест).
- **Отображение** (`bot_screens.py::format_ticker_behavior`) читает активный алерт `source_type='uport'` из той же таблицы `alerts`, что и брокерские -- никакого отдельного механизма отображения. **Фильтрует по `portfolio_id` контекста карточки** -- живой баг, найденный пользователем вживую: без фильтра карточка портфеля П10 показывала алерт другого портфеля (П136), просто как "последний по времени" (у разных портфелей, держащих одну бумагу, разные строки алертов). Починено.

Тестирование -- сквозное, реальным механизмом (не моком): backdated-запись в `quote_snapshots` (искусственно "состаренная" котировка) → реальный вызов `check_price_moves` → реальная запись в `alerts` → реальное уведомление в Telegram с настоящей кнопкой → пользователь жмёт кнопку вживую → проверка `is_active` в БД. Нашли и почини­ли по пути: (1) не почистили тестовый снэпшот после первого раунда -- следующий живой цикл котировок (после `restart_uport.sh`) сам наткнулся на тестовые данные и создал лишний реальный алерт независимо от тестового скрипта -- урок: чистить тестовые данные СРАЗУ, до следующего цикла синка, не после; (2) упомянутый выше баг фильтрации по портфелю.
