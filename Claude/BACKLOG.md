8. **Написан `CashDeploymentAdvisor`** (`analytics/cash_deployment_advisor.py`) — определяет избыточный кэш и подбирает кандидата + первый шаг лесенки входа. Алгоритм: `deployable_pool = реальный_кэш − Кэш/Резерв.rules_config['cash_min_untouchable_usd']`; если `deployable_pool < rules_config['cash_auto_invest_threshold_usd']` — рекомендаций нет. Реальный кэш считается без отдельного запроса к `accounts` — это алгебраическая сумма `virtual_free_cash_usd` по всем стратегиям портфеля (доли стратегий в сумме дают 100%, тождество проверено на живых данных обоих портфелей). Кандидаты — содержательные стратегии (`REVOLVER`/`CONSERVATIVE_ACCUMULATION`/`TREND_FOLLOWING`) с положительным slack, отсортированные по **проценту недофинансированности собственной цели** (`slack / ideal_budget_usd`), а не по абсолютному $ — иначе крупная по доле стратегия почти всегда выигрывала бы у мелкой. Слот на кандидата = `min(slack стратегии, остаток пула, total_capital × portfolio_max_asset_pct%)`; кандидат-тикер ищется прогоном уже существующего `TickerEvaluator` по всем не купленным в портфеле тикерам (945 бумаг — не проблема для ночного пакета, ~60-80 сек на портфель); размер сделки = слот × `budget_share_pct` шага 1 из `strategy_tactics` (на практике у всех трёх стратегий шаг 1 — рыночная заявка). Кандидаты, куда денег не хватило, и стратегии без единого проходящего кандидата — тоже попадают в отчёт с пояснением. Только рекомендации, никаких переводов/ордеров.

   По пути найден и обойдён системный баг с данными (не в этом модуле — см. Трек C, п.21): лондонские тикеры (`.L`) имеют рассинхронизированные `current_price`/`target_mean_price` (пенсы/фунты, разница ×90-150), из-за чего `GLEN.L` в тестовом прогоне побеждал конкурс кандидатов с фиктивным ranking=12239. Пользователь решил в принципе не рекомендовать лондонские бумаги для портфелей Freedom Broker (сама ФБ путает то же самое в своих прогнозах) — добавлен фильтр по биржам США (`XNYS`/`XNAS`/`ARCX`/`XNMS`/`EDGX`/`OTCM`) для портфелей с `brokers.short_name='FB'`, определяется динамически по `portfolios.broker_id`, а не хардкодом ID портфеля. Для Trading 212 ограничение не действует — вопрос пенсов/фунтов там сознательно отложен.

   Протестировано на живых данных: портфель 1 (Револьверная, недофинансирована на 67.6%) → кандидат `BSX` (США, ranking=77.08) вместо `GLEN.L`; портфель 2 (Консервативная, недофинансирована на 34.2%) → кандидат `SYF`, слот $9 304.47 (упёрся в лимит 7%), шаг 1 = 30% = $2 791.34 — не изменился фильтром, был и остаётся американским. *(2026-07-22, Трек A)*

9. **`cron_scheduler.py` защищён от повторного срабатывания "умных будильников" при рестарте процесса + честный статус выполнения.** Проверка (перед добавлением дайджеста в планировщик, по просьбе пользователя) вскрыла: у fundamentals/signals/дворника/ETF-декомпозиции нет никакой памяти "уже выполнялось сегодня" — только проверка текущего UTC-часа раз в час. Systemd-юнит `uport.service` настроен на `Restart=always, RestartSec=5`, и по логам (`journalctl -u uport.service`) сервис реально падает и перезапускается по нескольку раз в неделю (`oom-kill`, `signal`, `timeout`) — если рестарт попадёт на целевой час, задача триггернется заново. Тяжелее всего это ударило бы по `signals_sync` (пересчитывает весь Universe ~940 тикеров без фильтра по свежести — повтор = полный лишний прогон по Yahoo Finance, риск rate-limit) и `etf_look_through_weekly`; `fundamentals_sync` и `db_janitor` естественно самозащищены (фильтр по свежести/идемпотентные DELETE), повтор для них почти безвреден.

   Решение: новая таблица `public.cron_job_runs` (`job_name` PK, `last_started_at`, `last_finished_at`, `last_status`, `last_error_message`) — создана скриптом [`create_cron_job_runs_table.py`](../create_cron_job_runs_table.py). Универсальный враппер `run_daily_job_once(db_instance, job_name, coro_factory)` в `cron_scheduler.py`: проверяет по БД (не по переменной в памяти — та не переживает рестарт), выполнялась ли задача сегодня по UTC-дате; если нет — помечает `RUNNING`, выполняет, честно фиксирует `SUCCESS` или `FAILED` с текстом исключения (пробрасывает исключение дальше, чтобы существующий `try/except` в каждой петле тоже отработал). Применено к четырём будильникам: `fundamentals_sync`, `signals_sync`, `db_janitor`, `etf_look_through_weekly`. Этот же враппер будет использован для будущего дайджеста (Трек A, п.2).

   Сознательно не сделано сегодня (см. Трек C, пп.24-25): динамический расчёт часа закрытия рынка через `zoneinfo` (пользователь решил, что 1-2 часа смещения функционально не важны) и честные `PARTIAL`-статусы на уровне отдельных тикеров внутри батча (требует правок в самих синхронизаторах, не только в `cron_scheduler.py`) — сегодняшний фикс различает только "упало всё целиком" (долетело исключение) vs "нет".

   Протестировано: изолированный прогон `run_daily_job_once` на тестовой `job_name` — успешный вызов фиксирует `SUCCESS`; повторный вызов в тот же день пропускается (`last_started_at` не меняется); вызов на "вчерашней" записи с падающей задачей корректно пробрасывает исключение и фиксирует `FAILED` с текстом ошибки. *(2026-07-22, Трек A)*

11. **`TickerEvaluator` переведён на пакетный скан (батч-фетч) + новый экран «Предложения» в Telegram.** Обнаружено при обсуждении новой кнопки: поиск кандидата (и в `CashDeploymentAdvisor`, и в задуманном экране идей) перебирал ~945 тикеров по одному (N+1 запросов к БД, ~60-80 сек на скан) — для интерактивной кнопки в Telegram неприемлемо. По тщательному разбору архитектуры (не переносить условия отбора в SQL/view — это раздвоило бы единственный источник правды правил между Python и SQL, а на 945 строках выигрыша в скорости всё равно не даёт, весь выигрыш — от устранения N+1) реализовано так:
   - Три чистые функции без обращения к БД — `TickerEvaluator._score_revolver/_score_conservative/_score_trend(f, rules_config, days_to_report)` — извлечены из прежних трёх инлайн-блоков `evaluate_ticker_strategy`, поведение не изменено (сверено на живых данных: NFLX ranking=66.56 для Револьверной — совпадает бит-в-бит с прежним прогоном).
   - Новый метод `TickerEvaluator.screen_universe_for_strategy(strategy_id, exclude_ticker_ids, us_only)` — один `SELECT` по всем тикерам (с фильтром по биржам США, если нужно) + один запрос конфига стратегии, дальше цикл по уже загруженным в память строкам вызывает те же `_score_X`. Ускорение: с ~60-80 сек до ~0.3-0.4 сек на скан.
   - `CashDeploymentAdvisor._find_best_candidate` упрощён — теперь просто берёт первый результат нового метода вместо собственного цикла; убрана дублирующая константа `US_EXCHANGE_CODES` (перенесена на `TickerEvaluator`, `CashDeploymentAdvisor` её больше не хранит). Полный `evaluate_deployment` теперь ~1 сек на портфель вместо ~60-80 сек; `assemble_portfolio_digest` — ~2 сек вместо ~80 сек.
   - Заодно почищен реальный баг, найденный при живом разборе рекомендации SYF (пользователь заметил, что она упала на 4% после выдачи, разбор показал конкретную причину): `debt_to_equity=NULL` в `_score_conservative` раньше тихо читался как `0.0` и автоматически проходил порог `< 1.5` — тот же анти-паттерн, что уже чинили в `PositionExitEvaluator` для выхода, здесь — для входа. Теперь `NULL` у любого из пяти фундаментальных полей Консервативной (ROE, долг, рост выручки 3г/текущий, P/E) даёт статус `N/A` (не считается провалом, но и не подделывает `PASS`).
   - Новый экран в Telegram: кнопка «💡 Предложения» в карточке стратегии (`bot_handlers/strategies.py`) → список топ-10 кандидатов кнопками (`process_strategy_ideas`) → клик по кандидату показывает обоснование (`process_view_idea_reason`, PASS/FAIL/N/A по каждому критерию с человекочитаемыми подписями, `METRIC_LABELS`). Обоснование пересчитывается заново по клику (дёшево — один тикер, не кеш), не хранится между списком и деталью.
   - Разбор факта также показал конкретную причину, почему `NFLX` выглядит тревожно (падает с середины апреля): прошёл отбор не по развороту MACD (он у него всё ещё отрицательный, реального разворота нет), а по запаздывающему сигналу "рекомендация аналитиков ≤ 2.0"; кроме того, `signal_next_report_date` уже в прошлом (-7 дней) — буфер отчёта защищает только от ПРЕДСТОЯЩЕГО отчёта, не от рекомендации сразу ПОСЛЕ него. Не исправлено сегодня (отдельный вопрос калибровки правила, не баг реализации) — стоит обсудить отдельно, возможно в связке с методикой валидации параметров (журнал рекомендаций / бэктест на исторических котировках, обсуждались, но не решены).
