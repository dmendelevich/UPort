# Материал для следующей сессии: стандартизация карточек портфеля и стратегии (подготовлено 2026-07-26)

Тема карточки **тикера** закрыта целиком (header/body/footer, PriceMoveWatcher, мультивалютность — см. [05_strategy_screen_and_kubiki.md](05_strategy_screen_and_kubiki.md), там же полная хронология). Следующая тема — та же работа для карточек **портфеля** и **стратегии**. Этот файл — конспект, чтобы не пересказывать правила и стандарты заново.

## Правила взаимодействия (не меняются, см. [01_workflow_rules.md](01_workflow_rules.md))

1. Тему и направление задаёт пользователь — не предлагать новые темы самостоятельно.
2. Фиксированная последовательность по каждой теме: (1) пользователь инициирует, (2) вместе смотрим, что уже сделано (код + документация — **не полагаться на память, перепроверять код каждый раз**, память могла устареть), (3) подробно обсуждаем принципы/алгоритм **без кода**, (4) код — только после явного подтверждения, что всё согласовано.
3. Код не готов, пока не протестирован (см. процедуру тестирования ниже).
4. Коммит — прямо в `master`, после завершения темы; **перед каждым `push` — отдельное явное подтверждение**, даже если "коммитить после темы" уже давно согласовано.
5. Перед любым `DELETE` на живой БД — сначала `SELECT` и осмотреть, даже "просто на всякий случай".
6. UPort — advisory-only: советует, никогда сам не исполняет сделки/переводы.
7. "Снэпшот, не архив" — не предлагать постоянное хранение истории, запрашивать у брокеров/Yahoo на лету. **Одно сознательное исключение уже есть** (`quote_snapshots`, короткий кольцевой буфер для `PriceMoveWatcher`, ограничен по размеру, не архив) — если для портфеля/стратегии всплывёт похожая потребность, решать так же явно, не по умолчанию.

## Процедура работы над "кубиками" экрана (отработана на тикере, использовать ту же)

1. **Найти ВСЕ живые варианты** экрана этого типа по всей кодовой базе через `grep` — не полагаться на память.
2. Разобрать общее (кандидат в переиспользуемую функцию) vs специфичное для контекста.
3. **Обсуждать пограничные случаи с пользователем явно**, не решать самостоятельно.
4. **Ключевой урок этой сессии**: раскладывать содержание не по "экранам", а по **смысловым блокам** — один и тот же блок может повторяться на разных экранах (пример: у тикера блок "финансовая характеристика" появляется и в карточке владельца, и как доп. секция "где ещё"). Первая попытка классифицировать "по какому это экрану" оказалась неверным углом зрения.
5. Писать общую функцию-сборщик в `bot_screens.py` (текст) или `bot_keyboards.py` (клавиатуры) — **одна функция на тип сущности/блока**, не одна на всё приложение.
6. Мигрировать каждое найденное место **по одному**, не всё разом.
7. Тестировать **послойно**, не только текстовым выводом в терминале:
   - прямой вызов новой функции на реальных данных БД (через `venv`);
   - мок-прогон полного хэндлера (`unittest.mock`, реальные `MenuAction`/DB), плюс регрессия остальных контекстов;
   - реальное тестовое сообщение в Telegram (`aiogram.Bot`, тот же `TELEGRAM_TOKEN` из `.env`) — **для визуальных/ширинных решений терминал не показывает реальную картину** (он сам моноширинный), обязательно смотреть живой скриншот.
8. После блока/темы — `restart_uport.sh` + проверка вживую самим пользователем. Несколько раз именно на этом шаге находились реальные баги, которые не всплывали в моках.
9. Записывать решения в заметки **сразу по ходу**, не откладывать. Бэклог: открытые пункты нумеруются **отдельно на каждый Трек** (у Track B и Track C, например, есть свои независимые №29/30/31 — это не коллизия, разные секции); раздел "Сделано" — отдельная сквозная нумерация.

## Технические стандарты, уже готовые (не изобретать заново)

### Ширина экрана и текст сообщений (`bot_handlers/bot_screens.py`)
- `SCREEN_WIDTH_CHARS = 22` — откалибровано **вживую** на iPhone 12 пользователя (не наугад).
- `SEPARATOR_WIDTH_CHARS = 12`, `SEPARATOR_LINE` — короче основной ширины (символ `─` визуально шире буквы, длинная черта "уезжала").
- `wrap_screen_line(prefix, content)` — перенос ОДНОРОДНОГО текста; `wrap_param_line(prefix, params, separator)` — перенос строки из НЕСКОЛЬКИХ параметров (не рвутся по словам); `justify_line(left, right)` — прижатие по краям, считает по ВИДИМОЙ длине (без markdown-разметки).
- **Важный нюанс**: шрифт сообщений Telegram пропорциональный, не моноширинный. Посимвольное выравнивание (`justify_line` и т.п.) даёт согласованное число знаков, но не идеальный пиксельный край — **особенно заметно на нескольких строках подряд** (колонка чисел). Решение, найденное в этой сессии: заворачивать именно такую колонку в моноширинный `` `code` ``-спан (одинарные backtick), не весь текст целиком (теряется `**bold**`/`*italic*`/эмодзи).

### Кнопки (`bot_handlers/bot_keyboards.py`) — ДРУГОЙ механизм, не путать с текстом сообщений
- LEGO-конвейер (`assemble_lego_line` + `build_smart_badge`/`build_ticker_block`/`build_name_block`/`build_number_block`/`build_finance_block`/`build_percent_block`/`build_separator_block`) — использует спецсимволы фиксированной ширины (`EN_SPACE`, `FIGURE_SPACE`, `BRAILLE_EMPTY`, `SIX_PER_EM`), которые стабильной ширины в ЛЮБОМ шрифте, не только моноширинном — поэтому кнопки можно выравнивать посимвольно без описанной выше проблемы.
- Уже готовые высокоуровневые сборщики: `generate_portfolio_button_text` (строка актива портфеля/позиции стратегии), `generate_strategy_button_text` (строка стратегии в списке), `generate_watchlist_button_text` (строка списка наблюдения).

### Header/body/footer архитектура (полностью — см. [05_strategy_screen_and_kubiki.md](05_strategy_screen_and_kubiki.md))
- **Header** — одна функция-сборщик НА ТИП СУЩНОСТИ, не одна на всё. Готово: `format_premium_header` (тикер), `format_strategy_header` (стратегия). **Портфель — ещё инлайн** в `portfolios.py` (не стандартизирован, это будет одна из первых задач).
- **Body** — смысловые блоки (см. процедуру, п.4). Для тикера получилось 5 реализованных блоков (финансовая характеристика, поведение, рыночные сигналы, связь с брокером, где ещё есть/запланировано) + контекстные (риск-аудит/обоснование).
- **Footer** — 4 ряда сверху вниз, порядок обязателен: (1) разделитель+фраза (единый опциональный блок — разделитель ТОЛЬКО если есть фраза), (2) информационные кнопки/переключатель вкладок (`generate_tab_switch_keyboard`), (3) функциональные кнопки, (4) навигация (`generate_nav_back_keyboard`). Для портфеля/стратегии эти кубики уже частично используются — проверить, где именно, а где ещё инлайн.

### Стандарт времени (`ARCHITECTURE/Time.md` — пользователь явно указал прочитать в этой сессии)
- Все временные колонки — `TIMESTAMP(0) WITHOUT TIME ZONE`, хранение строго в UTC.
- SQL: `(CURRENT_TIMESTAMP AT TIME ZONE 'UTC')::timestamp(0)` (не голый `CURRENT_TIMESTAMP`).
- Python: `datetime.now(timezone.utc).replace(microsecond=0, tzinfo=None)` — наивный UTC-срез, без суффиксов пояса.
- Вывод времени человеку — пересчитывать в его локальный пояс (есть индивидуальное смещение в `public.users`).
- **Практический вывод, важный для кода**: разницу дат/времени считать **в SQL** (`EXTRACT`), не тянуть `datetime` в Python и не вычитать там — ответ шлюза СУБД приходит как JSON (даты — строки), а не нативный объект `datetime`.

### Деньги и мультивалютность
- `currencies.multiplier` — только для КАНОНИЧЕСКОГО слоя `tickers`/Yahoo (нативные единицы биржи, например пенсы для LSE). НЕ применять к брокерскому слою (`listings`/`assets`/`orders`/`alerts` — они уже в настоящих единицах).
- `currency_rates` хранит курсы ТОЛЬКО к USD (хаб) — для произвольной целевой валюты нужна двухшаговая конвертация через USD.
- `analytics/analytics_utils.py`: `convert_currency_amount` (плоская FX, брокерский слой) и `convert_to_base_currency` (с multiplier, канонический слой) — оба уже используют общий `_get_fx_rate`.
- Карточка тикера теперь мультивалютна: валюта СМОТРЯЩЕГО пользователя (`state: FSMContext` → `user_db_id`, уже сохранён при `/start` в `summary.py::cmd_start`, не переопределять личность заново → `public.users.base_currency`, по умолчанию USD). Курс считается **один раз за рендер**, передаётся параметром во все функции блоков — не каждый блок лезет в БД за курсом сам. Для портфеля/стратегии — тот же принцип, если там тоже есть денежные суммы (почти наверняка есть).

### Конфигурация — где что хранить
- `config.py` — системные/технические параметры (чанки, паузы, таймауты, пути).
- `settings.py` — бизнес-параметры и пороги ("инвестиционный манифест", как сформулировал пользователь) — например, пороги `PriceMoveWatcher`.
- Ширина экрана (`SCREEN_WIDTH_CHARS` и т.п.) — сознательно НЕ в `config.py`, а прямо в `bot_screens.py` (пользователь явно поправил это решение раньше) — она не общесистемный параметр, а локальная для функций форматирования.
