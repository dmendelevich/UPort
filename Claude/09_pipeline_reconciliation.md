# Сверка реальных сделок с `order_pipelines` — согласованные принципы (2026-07-24)

Тема открыта в рамках V1 (см. [08_v1_plan.md](08_v1_plan.md), направления "Стратегии"+"Аналитика", объединены). Отправная точка — пример пользователя с тикером `OPEN`: план (`order_pipelines`) ждал шаг "купить 1 шт", куплено 2 шт, вся дельта (не только излишек) ушла в `UNALLOCATED`, конвейер не продвинулся. Разбор кода — см. [BACKLOG.md](BACKLOG.md), Трек A, п.29.

Ниже — согласованные принципы будущего решения ("словами", по требованию пользователя — сначала бизнес-логика, потом алгоритм, только потом код). **Код не писался и не обсуждался предметно** — следующий шаг, когда до него дойдём, это перевести это в алгоритм.

## Почему текущее жёсткое сопоставление (точное совпадение количества) — не баг, а вынужденное временное решение
Пользователь сознательно сделал именно так, столкнувшись с нерешёнными вопросами:
- бумага может быть одновременно в двух стратегиях портфеля (два активных `order_pipelines` на один тикер);
- продажи дают отрицательную дельту (заложено сознательно — `strategy_assets`/дельта в коде не завязаны на знак);
- бывает, что для одной стратегии по тикеру нужна покупка, а для другой (или после переоценки) — перенос/продажа.
Эти вопросы и разбираются ниже.

## Согласованная модель жизненного цикла идеи (от идеи до исполнения)
1. **Идея → план.** Число шагов и доля бюджета на шаг уже есть в `strategy_tactics` (`step_number`, `budget_share_pct`). У Консервативной шаги 2-3 уже описаны как **относительное условие**, а не абсолютная цена: `trigger_conditions = {"mode": "limit", "max_rsi": ..., "price_drop_pct": ...}`. У Револьверной шаг 2 — `trigger_conditions = {}` (недоделано, см. ниже). У Трендовой — один шаг (верно по смыслу, усреднение вниз ей противоречит).
2. **Шаг 1 переводится с рыночной заявки на лимитную** (решено — см. ниже про цену/условие).
3. Пользователь сам ставит лимитный ордер в терминале брокера (принцип "система только советует" не меняется). Ордер появляется в `orders` (уже синхронизируется, есть `broker_order_id`).
4. **Привязка конкретного ордера к конкретному шагу плана — вручную через бота, на первом этапе.** Пользователь явно указывает боту "этот ордер — это шаг N стратегии X". Автоматическое сопоставление (по тикеру+стратегии+направлению, с уточнением у пользователя только при неоднозначности) — возможное развитие позже, не сейчас. Именно эта привязка снимает проблему "бумага в двух стратегиях": неоднозначность разрешается явным указанием, а не угадыванием по количеству.
5. **Исполнение (fill).** Там, где брокер даёт историю сделок с привязкой к ID ордера (у ФБ — `getTradesHistory`, поле `order_id`) — сверяем точно, включая частичные исполнения. Там, где брокер этого не даёт (Т212 — неизвестно, будущие брокеры — тоже неизвестно) — деградация до нынешнего механизма "снимок позиции", но с почином: **частичный зачёт вместо "всё или ничего"** (излишек/недостача относительно ожидаемого — в `UNALLOCATED`, а не вся дельта целиком). Это и даёт универсальность: базовый уровень работает для любого брокера, брокеры с богатым API дают точность бесплатно.
6. **Переход на следующую ступень.** Условие шага (напр. `price_drop_pct`/`max_rsi`) пересчитывается заново каждый цикл (в дайджесте), не хранится как разово вычисленная цифра — поэтому оно не может "протухнуть" так, как протухла лимитная цена в $100, поставленная 2 месяца назад и с тех пор недостижимая. Уже стоящие, давно не исполненные ордера — отдельно попадают в проверку "не устарел ли" (см. открытый пункт бэклога №5, обязателен для V1).

## A) Цена/условие для шага 1 (был рыночным, переводим на лимит)
Решено использовать сигнал разворота тренда падения, на основе уже существующих полей `tickers` (`signal_macd`, `signal_ema_20`, `signal_rsi` — считаются в `sync_signals_yf.py` из годового ряда Yahoo Finance, `period="1y"`, но в базу пишется только последнее значение).

**Найдено и исправлено по ходу обсуждения:**
- **Настоящий "кросс" (пересечение линий именно в этот день) сейчас не отследить** — `sync_signals_yf.py` уже тянет годовую историю для расчёта индикаторов, но сохраняет только `.iloc[-1]`, вчерашнее значение выбрасывается. Решение дешёвое (без новых обращений к API — история и так уже в памяти при расчёте): дополнительно сохранять предыдущее значение / флаг "развернулось за последние N дней". Не сделано сейчас — пункт для будущей реализации.
- Идея пользователя использовать `getHloc` ФБ (историю свечей, доступна по любому тикеру через `ticker_name_map`, не только по бумагам, реально держащимся у ФБ) — хорошая и универсальная, но избыточна для этой конкретной задачи: Yahoo уже даёт нужное и уже интегрирован. Держим в уме как запасной источник на будущее.
- **Найдена и исправлена ошибка слоёв в черновике предложения:** `tickers.current_price` — НЕ живая котировка, это батчевый снимок, пишется только из `sync_signals_yf.py` (по факту вчерашнее закрытие). Живая/часто обновляемая цена — `listings.last_price` (брокерский слой, свой цикл синхронизации котировок). Для проверки условия и для цены самого лимитного ордера нужно использовать `listings.last_price` конкретного портфеля/листинга, а не `tickers.current_price`. Та же по сути ошибка (смешение канонического и брокерского слоя), что уже поймана в BACKLOG.md п.21 (пенсы/фунты у лондонских тикеров) — принцип разделения слоёв подтверждён ещё раз.

Рабочая (пока не финальная, пороги не зафиксированы) комбинация условия разворота: `signal_macd` устойчиво положителен + `listings.last_price > signal_ema_20` + `signal_rsi` вышел из зоны перепроданности. Точные пороги — при переходе к алгоритму/коду.

## B) Привязка ордер↔шаг
Решено: начинаем с ручного подтверждения в боте (пользователь сам говорит боту, какой ордер к какому шагу относится). Автоматическое сопоставление — возможное развитие потом, если появится необходимость.

## C) Ступенчатый выход (продажи)
Решено: выход — тоже лесенка, с пределом в 1 шаг для стратегий, где полный единовременный выход достаточен. Отдельная таблица не нужна — `order_pipelines`/`strategy_tactics` уже не завязаны на знак дельты (сознательное решение пользователя ещё на этапе проектирования `strategy_assets`). `PositionExitEvaluator` в будущем должен не сразу выдавать "продавай", а заводить/обновлять exit-pipeline с нужным числом шагов из тактики стратегии.

## D) Перенос между стратегиями — предложено объединить в одну функцию
Пример пользователя: AMD куплена до системы, росла 3 месяца подряд — если бы лежала в Револьверной, через 30 дней система заставила бы продать, хотя тренд явно продолжался. Пользователь подтвердил: это применимо в обе стороны и относится не только к этому случаю. Один и тот же тип рекомендации ("перенести позицию в другую стратегию", механизм переноса частично уже есть — `bot_handlers/strategies.py`/`generate_target_strategies_keyboard`, прямая перезапись владения в `strategy_assets`, без реальной сделки у брокера) применим к нескольким триггерам:
- истёк тайм-аут Револьверной, но моментум ещё жив (уже открытый вопрос BACKLOG.md п.2);
- обратный случай — тренд ломается, но бумага может подойти другой стратегии;
- позиция в `UNALLOCATED`, структурно подходящая под конкретную стратегию;
- перекос доли/переинвестированность стратегии (BACKLOG.md п.4) — перенос вместо продажи+покупки.

**Отнесено к теме "Аналитика"** (следующий этап после текущего аудита pipeline, см. [08_v1_plan.md](08_v1_plan.md)) — не решается предметно сейчас, только зафиксирован как единый будущий модуль вместо нескольких разрозненных.

## E) `trigger_conditions` шага 2 Револьверной (сейчас `{}`)
Оставлено как есть. Пользователь подтвердил: текущий набор стратегий — черновик для отладки, не догма; содержательный пересмотр (в т.ч. этого пункта) — предмет будущего блока "Аналитика", не этого аудита.

## Что переносится в тему "Аналитика" (не решать в рамках текущего аудита)
- Единая функция "кандидат на перенос между стратегиями" (п. D).
- Содержательный пересмотр `trigger_conditions`/`rules_config` по всем стратегиям (п. E), включая шаг 2 Револьверной.
- Сохранение предыдущего значения индикаторов в `sync_signals_yf.py` для настоящего обнаружения "кросса" (п. A) — небольшая, но отдельная доработка.

## Ещё не обсуждено (всплывёт при переходе к алгоритму)

- Что делать с легаси-позициями без `order_pipelines` вообще (GLDM/PG/UBER, BACKLOG.md «Сделано» п.22), когда для них сработает новый ступенчатый выход — заводить им pipeline задним числом или нет.

## Итоговый алгоритм и ТЗ (согласовано 2026-07-24, готово к реализации)

**Находка по ходу проектирования:** `sync_account_fb.py` (распределение сделок по стратегиям) вызывается не по таймеру, а из WebSocket-слушателя ФБ (`fb_websocket_daemon.py::listen_freedom_broker`, живые потоки `portfolio()`/`orders()`) — реагирует за секунды. Значит уведомление об исполнении шага не требует отдельного "срочного канала" (это другой, более широкий и всё ещё не решённый вопрос — BACKLOG.md п.1, про алерты по цене/RSI на медленном 5-минутном опросе) — достаточно вызвать `bot.send_message` в момент, когда сверка уже (в реальном времени) подтвердила исполнение шага. Специфично для ФБ — есть ли аналог у Т212, неизвестно (тот же вопрос универсальности, что и с историей сделок).

**Схема:** добавить `order_pipelines.pending_broker_order_id` (varchar, nullable) — какой ордер брокера сейчас ожидается на `current_step`; очищается, когда шаг засчитан. Новых таблиц не нужно (выход переиспользует ту же таблицу со знаком).

**Сценарий в боте (создание плана + привязка ордера — одно действие):**
Кнопка «🔗 Привязать ордер к плану» на карточке тикера (виден, только если есть хотя бы один активный `orders`-ордер по этому тикеру/портфелю без `pending_broker_order_id`). Пользователь выбирает ордер из списка.
- Если по тикеру+портфелю уже есть ACTIVE `order_pipelines` — это шаг существующего плана, просто проставляем `pending_broker_order_id` на `current_step`.
- Если нет — новый план: бот спрашивает стратегию (из активных content-стратегий портфеля, куда тикер проходит по `TickerEvaluator`) и **итоговое количество на весь план (`target_quantity`) — решено вводить вручную**, всегда (не подставлять дефолт от слота `CashDeploymentAdvisor`). Автоподстановка дефолта из уже посчитанного слота — отложена в бэклог как отдельное упрощение (см. BACKLOG.md).

**Уведомление о шаге:** `bot` прокидывается в `FreedomBrokerSyncManager`/`SyncStrategyAssetFB` (по аналогии с `cron_scheduler.start_clocks(db_instance, bot)`), сообщение реальному владельцу портфеля (не хардкод на админа, как в дайджесте v0), в момент `NEXT_STEP`/`COMPLETE_PIPELINE`. Текст: *"✅ Шаг {N} плана по {symbol} ({strategy_name}, портфель {name}) исполнен: {qty} шт по {price}. Распределено в стратегию."*

**Устаревание ордера:** проверка в цикле обновления котировок (`sync_quotes_fb_autonomous`, раз в 15 мин) — сравнение `orders.p` с `listings.last_price`. **Порог: >5% от цены ордера.** Уведомление разово при первом пересечении порога (не на каждом цикле) — дальше отражается в дайджесте как уже отмеченное.

**Выход:** `PositionExitEvaluator` не создаёт pipeline сам — рождается тем же сценарием привязки ордера, когда пользователь реально продал.

**Порядок реализации (частями, с тестом после каждой):**
1. Поле в БД + сценарий бота (создание плана / привязка ордера).
2. Логика сверки: линковка по `pending_broker_order_id` (снимок позиции + частичный зачёт вместо "всё или ничего"), без истории сделок ФБ пока.
3. Уведомление о шаге (прокидка `bot`).
4. Наблюдатель за следующей ступенью в дайджесте (пересчёт `trigger_conditions`, от средней цены уже исполненных шагов).
5. Проверка устаревания ордеров (порог 5%).
6. История сделок ФБ (`getTradesHistory`) как уточнение поверх Tier 0 — отдельно, когда пользователь пришлёт доступ/детали API.

Обсуждение полностью согласовано 2026-07-24 — переходим к реализации.
