# Бумажный портфель — концепция и план реализации (согласовано 2026-08-03)

Тема выросла из разговора «как проверить систему на работоспособность» (Тренды 2). Рассмотрели два варианта — бэктест на истории и внешний сайт с виртуальными портфелями — и остановились на третьем: живой виртуальный портфель прямо внутри UPort, идущий вперёд от сегодняшнего дня по реальному суточному циклу.

## Зачем — две цели сразу, не один тест

1. **Проверка системы.** В отличие от бэктеста назад, у движения вперёд нет проблемы с историческими данными (система сознательно не хранит рыночную историю — «снэпшот, не архив», см. `CLAUDE.md`). Фундаментал (ROE/долг/P-E) и состав индекса (`tickers.provenance`) у Yahoo доступны только текущим снимком — бэктест назад ими автоматически подглядывал бы в будущее. Двигаясь ВПЕРЁД, этой проблемы нет вообще — бумажный портфель тестирует ВСЕ три стратегии честно, не только технический слой (слом тренда/лесенка/цель Револьверной), но и фундаментальный вход/выход Консервативной, и скрининг «мировых лидеров».
2. **Задел на будущее реальное исполнение.** Уже зафиксировано раньше (`11_asset_lifecycle_and_plan.md:57`, 2026-07-29): «по мере успешных боевых испытаний системе могут постепенно дать больше полномочий — вплоть до самостоятельного исполнения». Решено не тестировать заглушкой, а сразу строить механизм подтверждения (Да/Нет), который в будущем можно направить на реальный брокерский API, не переписывая логику решения.

## Принципы (согласованы по ходу обсуждения)

1. **Advisory-only не нарушается** — виртуальные деньги, реального брокера нет, авто-исполнения без подтверждения не будет.
2. **Подтверждение, не мгновенное авто-исполнение.** Каждая рекомендация уходит отдельным сообщением с кнопками Да/Нет. Это не только уважает принцип, но и снимает риск оптимистичного искажения теста (мгновенное идеальное исполнение вместо реалистичной человеческой задержки).
3. **Единая точка правды** — новое поле `portfolios.execution_mode` (`ADVISORY` | `CONFIRM`). `ADVISORY` — сегодняшнее поведение всех реальных портфелей (только текст). `CONFIRM` — рекомендация + кнопка, по «Да» система исполняет. Поле одновременно решает, нужно ли подтверждение, и какой механизм обновляет позиции портфеля (брокерский синк для `ADVISORY`, новый обработчик для `CONFIRM`) — не нужно два отдельных флага.
4. **`broker_id = NULL`, синтетического «бумажного» брокера не заводим.** Проверено: `tickers.ticker_name_map` не generic по таблице `brokers` (хардкод трёх ключей в `utils.py`, см. `BACKLOG.md` №54) — новый брокер сломал бы `ensure_listing()`. Листинг остаётся тем, чем был — ценой у РЕАЛЬНОГО брокера (ФБ/Т212). Бумажный портфель просто держит `assets`, ссылающиеся на обычные реальные FB-листинги (те же, что у П10/П136). Если кандидат ещё не имеет листинга — обработчик подтверждения сам вызывает `ensure_listing(ticker_id, broker_id=1)` напрямую (тот же приём, что уже применяет `strategies.py:323` для карточки обоснования кандидата), не через список наблюдения реального портфеля (не мусорим в чужих данных).
5. **`us_only = True`** — как у реальных FB-портфелей, для чистоты сравнения и чтобы не плодить листинги без реальных котировок.
6. **Деньги — обычная строка `accounts`, новая схема не нужна.** `broker_id`/`portfolio_id` в `accounts` nullable, FK на `brokers` вообще нет. Нужна одна строка: `portfolio_id` = id бумажного портфеля, `broker_id = NULL`, `account_number` — придуманный, гарантированно не пересекающийся с реальными (например `'PAPER-<portfolio_id>'`), `currency_id='USD'`, `cash_available` = стартовый капитал. Обработчик подтверждения двигает `cash_available` тем же способом, что и `sync_account_fb.py:115`.
7. **Владелец — dmend (`owner_id=1`), не сын.** У сына (owner_id=4, МДМ) реальный брокерский счёт (T212) ещё не подключён — если отдать ему бумажный портфель и он же первым пройдёт реальный онбординг, старый `LIMIT 1`-баг (см. Фаза 0) мог бы однажды перепутать его настоящие деньги с бумажными. У dmend этот путь кода никогда больше не выполнится (онбординг давно позади).
8. **Срок — 1 год, контрольная точка 2027-08-03.** Не жёсткий стоп, просто дата формальной оценки. Бенчмарк — CAGR портфеля против S&P500 (SPY) и против целевых ~15% годовых (`12_investment_goal_and_mechanisms_roadmap.md`).

## Параметры (согласованы 2026-08-03)

- Стартовый капитал — **$50 000**.
- Название портфеля — **«ПБум»**.
- Владелец — dmend (`owner_id=1`).
- Валюта — USD.
- Стратегии — заводские доли `recommended_share_pct` (Консервативная 50% / Трендовая 25% / Револьверная 15% / Кэш-Резерв 10%), все 5 шаблонов через существующий бутстрап `portfolio_admin.py`.

## Механика взаимодействия (день за днём)

**Область Фазы 2 (согласовано 2026-08-03) — только покупка.** «ПБум» сегодня пустой, продавать/подрезать/докупать по лесенке пока нечего — только `CashDeploymentAdvisor` даёт рекомендации. `PositionExitEvaluator`/`PortfolioRebalancer`/`LadderStepWatcher` подключаются позже, когда портфель реально что-то купит (см. `BACKLOG.md` №60 — стандартизация общего конверта рекомендации отложена до второго реального примера, не проектируется вслепую).

1. В том же суточном цикле, что дайджест — новая функция (аналог `send_daily_digests`) прогоняет `CashDeploymentAdvisor.evaluate_deployment` по портфелям с `execution_mode='CONFIRM'`.
2. Каждая рекомендация (`status='CANDIDATE_FOUND'`) — **отдельное** сообщение в Telegram с кнопками «✅ Да» / «❌ Нет» (не бандл всех сразу — паттерн `generate_confirm_keyboard`, уже используемый для удаления из СН, `bot_handlers/watchlist.py:407-462`).
3. **Да** → обработчик **перепроверяет заново**, не исполняет старыми числами из утреннего сообщения: кандидат всё ещё проходит критерии стратегии, слот пересчитан от ЖИВОГО `accounts.cash_available` (могло измениться, если другая рекомендация того же цикла уже исполнена). Если условия изменились — сообщение редактируется на "⚠️ Условия изменились, кандидат больше не актуален", без исполнения.
   - Если у кандидата ещё нет листинга — `ensure_listing(ticker_id, broker_id=1)`; **обязательна проверка `last_price > 0`** после (см. `BACKLOG.md` №59 — `ensure_listing` может молча вернуть цену 0, для брокерных портфелей это самоисцеляется следующим синком котировок, для бумажного — нет) — при `0` не исполнять, сообщить "не удалось получить цену, попробуй позже".
   - Запись **напрямую** в `assets` (новая строка — позиции ещё не было)/`strategy_assets`/`order_pipelines`/`accounts.cash_available` — НЕ через `SyncStrategyAssetFB.distribute_asset_delta` (не подходит: требует, чтобы `assets` уже существовала, а для первой покупки её ещё нет — см. `BACKLOG.md`, разбор при проектировании).
   - После исполнения — `edit_text` на статус "✅ Исполнено: N шт по $X", кнопки заменяются (не остаются висеть).
4. **Нет** → сообщение редактируется на "❌ Отклонено", без записи в БД. Отказ не запоминается — если условие всё ещё верно, кандидат просто появится снова на следующий день (то же поведение, что и у обычного дайджеста сегодня, никакого нового механизма snooze для v1).
5. Раз в сутки — снимок стоимости портфеля в новую таблицу `portfolio_value_history(portfolio_id, snapshot_date, total_value)`. Специально сделана не только для бумажного портфеля — это же прямое попадание в п.9 дорожной карты («Измерение фактической эффективности стратегий», `12_investment_goal_and_mechanisms_roadmap.md`) — реальные П10/П136 смогут переиспользовать ту же таблицу позже без изменения схемы.
6. Отчёт CAGR/сравнение с SPY — для v1 просто SQL-запрос по `portfolio_value_history`, не отдельный экран бота (строить экран, если понадобится позже, не заранее).

## Что уже проверено и не требует новых решений

- Дайджест подхватит новый портфель без доп. проводки — `cron_scheduler.py:135`, безусловный цикл по всем `portfolios`.
- Бутстрап всех 5 стратегий не завязан на брокера — `portfolio_admin.py:231-256`, `CROSS JOIN strategy_templates`.
- `accounts.cash_available` можно двигать без всякого брокера — обычный `UPDATE`.
- `order_pipelines_unique_active_run` — частичный индекс (только `PENDING`/`ACTIVE`) уже реально стоит в БД (проверено запросом к `pg_indexes` 2026-08-03) — несколько циклов по одной бумаге+стратегии за год не заблокированы, чинить нечего.
- `sync_alerts_fb.py`/`sync_account_fb.py`/`main.py`-websocket жёстко отфильтрованы на `broker_id=1`/реальные `account_number` — бумажный портфель (`broker_id=NULL`, синтетический `account_number`) физически не может быть подхвачен реальным брокерским синком.
